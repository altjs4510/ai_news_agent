## 한글 요약

Python 3.15는 표준 라이브러리를 조금씩 손보는 통상적인 릴리스가 아니라는 것이 이 글의 전제다. 새 문법, 새 내장 타입, 제대로 된 프로파일링 도구, 개선된 JIT을 통한 실행 속도 변화, 그리고 파이썬의 기본 텍스트 인코딩이라는 근본적인 것까지 바뀐다. 글을 쓴 2026년 8월 시점에 3.15는 아직 프리릴리스지만 **기능 집합은 이미 동결**돼 있어, 프로덕션에 올리기보다 테스트해 볼 적기라는 것이 저자의 입장이다.

실험 환경은 uv로 격리하길 권한다. `uv init` 후 `uv python install 3.15` / `uv python pin 3.15`로 프로젝트별 버전을 고정하고, `lazy import` 같은 3.15 전용 문법을 쓸 거라면 pyproject.toml에 `requires-python = ">=3.15"`를 명시하라는 것이다. 기존 설치본을 건드리지 않고 버전을 프로젝트에 못 박는 방식이다.

**1) `lazy import` — 지연 임포트가 드디어 언어 기능으로.** 큰 애플리케이션은 해당 실행에서 실제로 쓰지도 않는 모듈을 임포트하느라 상당한 기동 시간을 쓴다. 지금까지는 임포트를 함수 안으로 옮기거나 `importlib`를 직접 쓰는 우회가 일반적이었다. 3.15는 `lazy` 소프트 키워드로 명시적 지연 임포트를 도입한다. 모듈은 평소처럼 모듈 스코프에 선언되지만 **해당 이름이 실제로 사용될 때까지 로딩이 미뤄진다.** 저자의 예제는 `lazy import json` 후 `sys.modules`를 확인해, 선언 직후에는 json이 로드되지 않았고 함수가 `json.loads()`에 접근하는 시점에야 해석되어 `sys.modules`에 들어가는 것을 보여준다. CLI, 대형 애플리케이션, 플러그인 시스템, 의존성 트리가 무거운 앱처럼 기동 시간이 중요한 경우에 유용하다. 전역으로 켜서 먼저 측정해 보는 것도 가능하다 — `uv run python -X lazy_imports=all main.py`로 기존 앱의 기동 시간이 개선되는지 벤치마크한 뒤, 어디에 명시적 `lazy import`를 둘지 결정하는 순서를 저자는 권한다. 핵심 개선은 성능만이 아니라, **읽는 사람이 기대하는 위치(모듈 최상단)에 임포트를 두면서도 기동 시 모든 의존성 비용을 치르지 않아도 된다**는 점이다.

**2) `frozendict` 등장.** 파이썬에는 불변 튜플과 frozenset이 오래 있었지만 대응하는 내장 매핑 타입이 없었다. 3.15가 이를 추가한다. 생성 후 변경되면 안 되는 설정값을 `frozendict({...})`로 만들면 실수로 대입할 때 `TypeError`로 즉시 실패한다. 더 중요한 건 키와 값이 해시 가능하면 **frozendict 자체가 해시 가능**하다는 점이다. 덕분에 `dict[frozendict, float]` 같은 캐시가 가능해진다 — 설정 객체, 캐시 키, 불변 메타데이터, 변경이 곧 버그인 API에서 "이 딕셔너리는 고치지 마세요"라는 관례에 의존하던 것보다 훨씬 깔끔하다.

**3) `sentinel()` — `_MISSING = object()` 관용구의 표준화.** `None`이 유효한 값인 경우 "호출자가 아무것도 주지 않았다"는 제3의 상태가 필요해서 익명 `object()`를 쓰던 패턴을, 3.15는 `sentinel("MISSING")` 내장으로 표준화한다. 기존 트릭과 달리 의미 있는 표현(repr)을 갖고, 동일성을 적절히 보존하며, 문서화된 조건에서 피클링을 지원하고, **타입 표현식에 직접 참여할 수 있다.** 작은 추가지만 실무 코드에서 보기 싫은 패턴 하나를 제거한다고 저자는 평가한다.

**4) 컴프리헨션에서의 언패킹.** 지금까지 중첩 구조를 평탄화하려면 `for` 절을 하나 더 써야 했다(`[row for batch in batches for row in batch]`). 3.15는 리스트·셋·딕셔너리 컴프리헨션 안에서 이터러블·매핑 언패킹을 직접 허용한다. 같은 동작이 `[*batch for batch in batches]`로 표현된다. 셋에서도 `{*columns for columns in column_groups}`로 여러 집합을 합쳐 중복을 자동 제거할 수 있고, 딕셔너리는 대응하는 `**` 언패킹을 얻어 `{**part for part in config_parts}`처럼 **설정 계층(기본값 → 환경별 → 런타임 오버라이드)을 병합**할 수 있다. 일반 딕셔너리 언패킹과 마찬가지로 같은 키가 여러 번 나오면 뒤의 값이 앞을 덮는다. 저자는 이것이 단순한 문법 설탕이 아니라고 본다 — 평탄화를 표현하려고 중첩 루프를 도입하는 대신, "컨테이너들의 모음을 순회하며 각 컨테이너를 결과로 언패킹한다"는 실제 연산을 직접 기술하게 해 주기 때문이다.

**5) UTF-8이 기본이 됨.** 인코딩 버그는 가장 재미없는 디버깅 대상이다. 3.15는 운영체제 환경과 무관하게 UTF-8을 기본 인코딩으로 삼는다. `open("customers.csv")`에 인코딩을 명시하지 않으면 이제 UTF-8이 쓰인다. 리눅스·윈도우·컨테이너·CI·클라우드를 오가는 코드에서 플랫폼 의존적 동작이 줄어든다. 다만 파일 포맷 자체가 인코딩을 규정하는 경우엔 여전히 명시하라고 권한다 — 명시적 인코딩은 훌륭한 문서화이며, 달라진 것은 **실수로 빠뜨렸을 때 동작이 주변 로케일에 좌우되지 않는다**는 점이다.

**6) 제대로 된 샘플링 프로파일러.** 3.15는 새 `profiling` 패키지와 함께 `profiling.sampling` 아래 고빈도 통계 샘플링 프로파일러 **Tachyon**을 도입한다. 개별 함수 호출을 계측하는 결정론적 프로파일러와 달리 주기적으로 실행 중인 프로그램을 관찰하므로, 상대적으로 낮은 오버헤드로 실제 애플리케이션을 조사하는 데 적합하다. 프로파일링 코드를 한 줄도 넣지 않고 `uv run python -m profiling.sampling run --mode=cpu main.py`로 돌릴 수 있고, `--flamegraph -o profile.html`로 인터랙티브 플레임그래프를 생성해 브라우저에서 볼 수 있다. 흥미로운 지점은 애플리케이션이 프로파일러의 존재를 전혀 모른다는 것이며, 3.15는 **이미 실행 중인 프로세스에 PID로 붙는 것**까지 가능하다. 고립된 벤치마크 함수가 아니라 장시간 도는 서비스와 데이터 파이프라인 진단에 훨씬 유의미해진다.

**7) JIT이 의미를 갖기 시작.** 실험적 JIT 자체는 3.15에서 새로운 것이 아니지만 상당히 향상됐다. 저자는 내부 구조보다 "평범한 파이썬 코드에서 차이를 측정할 수 있는가"를 묻고, NumPy 같은 네이티브 라이브러리가 아니라 파이썬 안에서 분기와 정수 연산이 도는 루프로 벤치마크한다. `-X jit=0`과 `-X jit=1`을 비교한 그의 측정값은 JIT 비활성 시 평균 0.411초, 활성 시 평균 0.374초 수준이었다. 다만 저자는 **모든 워크로드가 빨라진다고 기대하지 말라**고 못 박는다 — 자신의 머신에서 이 벤치마크는 트레이싱과 컴파일 오버헤드 탓에 JIT을 켰을 때 오히려 느려진 경우도 있었다. 3.15의 JIT은 더 유능해진 실험적 최적화 엔진이지 공짜 성능 스위치가 아니라는 것이 요점이다.

**보너스: 더 나은 오류 메시지.** 3.15는 의도했을 법한 속성이 **중첩된 객체에 존재하는 경우**를 인식한다. 래퍼나 응답 객체처럼 실제 데이터를 내부에 들고 있는 클래스에서 특히 유용하다. `Container`에 `shape`가 없다고만 알리는 대신 `Did you mean: 'inner.shape'?`처럼 제안한다. 또 JavaScript·Java·Ruby·C# 출신 개발자가 흔히 저지르는 메서드 이름 실수도 인식한다. lazy import나 JIT에 비하면 작지만, 진단 개선은 놀랄 만큼 많은 디버깅 시간을 줄여준다.

지금 3.15로 갈아탈 것이냐는 질문에 저자의 답은 **프로덕션은 아직**이다. 프리릴리스이고 공식 What's New 문서조차 초안 상태라고 경고하고 있다. 다만 기능이 동결됐으므로 테스트 환경을 만들어 기존 프로젝트를 돌려볼 적기다 — `uv python install 3.15` / `uv python pin 3.15` / `uv sync` / `uv run pytest`가 가장 유용한 실험이라는 것. 결론적으로 lazy import, frozendict, 제대로 된 sentinel, 컴프리헨션 언패킹, UTF-8 기본화, 대폭 개선된 프로파일링은 당장 코드 작성 방식에 영향을 주지만, 더 큰 이야기는 그 밑에 있다 — 빠르게 개선되는 JIT, free-threading 인프라, 더 나은 시스템 수준 관측 가능성으로 CPython이 **파이썬 개발자들이 그냥 안고 살아온 한계들**을 공략하기 시작했다는 점이다.

**적용 각도(참고용 메모)**: 이미 uv로 돌리는 프로젝트라 3.15 테스트 비용이 낮고, `lazy import`는 매 실행 전체 소스 모듈을 임포트하는 배치 파이프라인의 기동 시간에, `-m profiling.sampling`의 PID 어태치는 새벽 배치가 느려졌을 때 원인 추적에 바로 쓸 만하다.
