## 한글 요약

20년 넘게 금융 IT 보안을 해온 저자는 보안 업계를 세 시대로 나눈다: 인프라 시대, 클라우드 시대, 그리고 지금 시작되는 **에이전틱 AI 시대**. 핵심 주장은 에이전틱 AI가 "보안팀이 지켜야 할 기술이 하나 더 늘어난 것"이 아니라는 점이다. 지켜야 할 시스템의 성격, 상대해야 할 공격자, 나아가 보안 업무가 수행되는 방식 자체가 동시에 바뀐다.

인프라 시대의 논쟁은 "방화벽을 어디에 둘 것인가"였다. 내부망과 외부망이 있고 그 사이에 방화벽이 있으며, 원격 접속은 VPN, 엔드포인트엔 백신, 네트워크엔 IDS/IPS가 있었다. 경계 기반 모델이 현실에서 그렇게 단순했던 적은 없지만, 적어도 머릿속 그림은 말이 됐다. 클라우드 시대는 서버를 가상화한 게 아니라 애플리케이션 설계 방식을 바꿨다. 애플리케이션은 로드밸런서·API·Lambda·컨테이너·쿠버네티스·관리형 DB·큐·오브젝트 스토리지·서드파티 SaaS의 조합이 됐고, 잘못된 IAM 롤 하나가 방화벽을 거치지 않고도 환경 전체를 노출시킬 수 있게 됐다. **신원이 사실상 경계가 됐다.** 보안은 배포 마지막 단계에서 검사하는 역할을 그만두고 개발 수명주기 안으로 들어가야 했고, 그 결과 클라우드 보안 엔지니어·DevSecOps·제품 보안 엔지니어 같은 직무가 생겨났다. 저자가 짚는 중요한 패턴은 **공식 교육과 자격증은 언제나 기술이 이미 바뀐 뒤에 따라온다**는 것이다.

세 번째 시대의 정의적 특징은 조직이 AI를 쓴다는 게 아니라 AI가 **행동을 취하기 시작했다**는 것이다. 어시스턴트는 질문에 답하지만 에이전트는 문서를 읽고, DB를 조회하고, API를 호출하고, 코드를 쓰고, 설정을 바꾸고, 티켓을 만들고, 목표 달성에 어떤 순서가 필요한지 스스로 판단한다. 전통적 애플리케이션은 대체로 결정론적이다. 포트 22를 막는 방화벽 규칙은 포트 22를 막는다. 반면 같은 목표를 준 두 에이전트는 서로 다른 실행 경로를 낼 수 있고, 지시를 오해하거나, 악의적 데이터를 신뢰하거나, 잘못된 도구를 고르거나, 정당한 작업 중에 민감정보를 노출할 수 있다. 문서 안의 텍스트를 지시로 해석할 수도 있고, 요청한 사람이 갖지 않은 권한으로 다른 시스템을 호출할 수도 있다. 그리고 저자가 가장 위험하다고 꼽는 것 — **작업을 마친 뒤 "다 잘 됐다"고 보고할 수 있다**는 점이다.

이에 따라 보안 질문이 한 층 더 올라간다. 인프라 시대는 "이 장비가 저 장비와 통신할 수 있는가", 클라우드 시대는 "이 신원이 저 리소스에 이 행위를 할 수 있는가"였다면, 에이전틱 시대는 **"이 시스템이 애초에 이 결정을 내리도록 허용되어야 하는가"**를 묻는다. 취약점 관리 에이전트를 예로 든다. 취약점을 찾고, 영향받는 앱을 식별하고, 조치를 정하고, 코드를 고치고, 테스트를 돌리고, PR을 만들고, 배포까지 한다 — 판단이 틀리기 전까지는 훌륭하다. 취약점 설명문에 악성 지시가 섞여 있거나, 무관한 컴포넌트를 건드리거나, 테스트가 회귀를 못 잡거나, 다른 에이전트가 그 틀린 출력을 받아 다음 행동을 자동 실행하면 **하나의 실수가 연쇄반응이 된다**. 수십 년간 과도한 권한(excessive permission)을 얘기해 왔다면, 이제 **과도한 자율성(excessive autonomy)**이 그만큼 중요해진다. 저자가 제시하는 보안 아키텍처 공식은 `최소 권한 + 최소 자율성 + 최대 관측 가능성`이다. 중요한 결정은 추적 가능하게, 파괴적 행위는 가능한 한 되돌릴 수 있게.

SOC에 여러 에이전트가 협업하는 그림도 제시된다. 하나가 탐지하고, 하나가 조사하고, 하나가 위협 인텔을 조회하고, 하나가 엔드포인트를 격리하고, 하나가 인시던트를 열고, 하나가 커뮤니케이션 초안을 쓴다. 정적 규칙 실행이 아니라 협업과 판단이므로 이들은 서로 이견을 내거나, 오해하거나, 잘못된 정보를 전파할 수 있다. 그래서 새로운 아키텍처 질문이 생긴다 — 어느 에이전트가 어느 에이전트를 신뢰하는가, 에이전트는 어떻게 인증하는가, 권한을 위임할 수 있는가, 실행 중에 새 권한을 획득할 수 있는가, 컨텍스트가 오염되면 어떻게 되는가, **주장한 것이 아니라 실제로 한 일을 어떻게 검증하는가**, 사후에 그 결정을 재구성할 수 있는가.

직무별 변화도 구체적이다. SOC 1선 분석가의 반복 조사 업무(로그 수집, IP 확인, 이벤트 상관분석)는 에이전트가 잘하게 되는 영역이라 직무가 속에서부터 비워진다. 분석가는 조사 워크플로를 설계하고, 에이전트의 결론을 검토하고, 자동화 불가능한 모호한 케이스를 처리하고, 지난주 에이전트가 왜 틀렸는지 파악하는 사람이 된다. 보안 엔지니어는 개별 스크립트 작성보다 **전체 구조 결정**(어디까지 자동 결정을 허용할지, 에이전트가 어떤 신원을 쓸지, 실패하면 어떻게 될지, 어디에 사람이 남아야 할지)으로 범위가 올라간다. 가장 크게 바뀔 곳으로 저자는 GRC를 꼽는다. 스프레드시트·설문·증거 수집·통제 매핑은 자동화 적합도가 높고, 살아남는 역할은 통제 매트릭스를 유지하는 사람이 아니라 **지속적으로 컴플라이언스를 증명하는 시스템을 설계하는 사람**이다. 여기에 에이전트 자체를 거버넌스하는 새 과제(무엇을 결정할 권한이 있는지, 어떤 증거를 보관하는지, 사람의 감독을 어떻게 입증하는지, 자율 시스템이 틀렸을 때 누가 책임지는지)가 더해진다.

실무 조언도 층위별로 나뉜다. 신입에게는 화려한 상위 계층을 좇느라 기본기를 건너뛰지 말라고 한다 — IAM·네트워킹·인증을 모르면 에이전트의 폭발 반경을 추론할 수 없고, API를 모르면 도구 오용을 이해할 수 없다. 다만 이번 전환에는 이전과 다른 기회가 있다. 클라우드 때는 "클라우드 경험이 있어야 클라우드 보안 일을 준다"는 고전적 함정이 있었지만, 에이전틱 AI는 **직접 경험을 만들어낼 수 있을 만큼 접근성이 좋다.** 도구 두세 개를 붙인 간단한 에이전트를 만들고, 일부러 과도한 권한을 준 뒤 무슨 일이 벌어지는지 보고, 읽는 문서 안에 악성 지시를 심어 도구 호출을 조작해 보고, 그다음 권한을 좁히고 승인 게이트를 넣고 로깅과 위협 모델링으로 보안을 입히라는 것이다. 자격증이 생기길 기다리지 말라는 조언이며, 동시에 SNS 요약이 아니라 **1차 자료**(OWASP의 LLM·에이전틱 보안 작업, 목표 하이재킹·도구 오용·권한 남용·에이전틱 공급망 리스크, 그리고 도구가 모델에 어떻게 노출되는지 이해하기 위한 MCP 명세)를 읽으라고 못 박는다.

경력 10~20년차에게는 경험이 부채가 아니라 해자라고 말한다. 위협 모델링, 신뢰 경계 이해, PPT에서는 완벽하지만 운영에서 무너지는 통제를 아는 감각은 그대로 전이된다. 위험한 쪽은 특정 제품 콘솔 조작 지식이 전문성의 대부분인 경우다. 실행 조언은 **인벤토리부터**다. 조직 안에는 이미 보안이 공식적으로 목록화하지 않은 에이전트들이 돌고 있을 가능성이 높다 — SDLC 안의 코딩 어시스턴트, SaaS에 켜져 있는 에이전틱 기능, 사내 지식베이스에 연결된 AI, 장기 API 토큰으로 돌아가는 누군가의 자동화. 엔지니어링에 어떤 코딩 에이전트가 CI/CD 안에서 돌고 어떤 자격증명을 쥐고 어디까지 닿는지 물어보라고 권한다.

위험 판별용 간단한 아키텍처 테스트도 제시된다. 에이전트가 ① 비공개 데이터에 접근 가능하고 ② 신뢰할 수 없는 입력을 소비하며 ③ 외부로 나가는 채널을 가질 때 — 세 조건이 동시에 성립하면 위험이 급격히 커진다. 이때 프롬프트 필터를 하나 더 얹기보다 **세 요소 중 하나를 구조적으로 제거**하라는 것이 핵심 처방이다. 아키텍처 통제가 "얌전히 굴어라"는 지시문보다 강하다. 신원 문제도 강조된다. 에이전트가 사람의 자격증명을 빌려 쓰게 두지 말고 고유 신원·범위 제한 권한·단기 토큰·요청 단위 인가를 주라는 것으로, 클라우드에서 서비스 계정과 워크로드 아이덴티티로 이미 배운 교훈을 PoC 편의를 이유로 반복하지 말라는 경고다. 도구 단위가 아니라 **역량(capability) 단위 거버넌스**도 권한다 — 데이터웨어하우스 읽기, 티켓 생성, 소스 수정, 외부 메일 발송, 프로덕션 배포 각각을 한 번 결정해 일관되게 강제하라는 것. 도구를 개별 승인하다 보면 조달 에이전트가 재무 시스템·계약·메일에 동시에 접근하고 있는 상황을 뒤늦게 발견하게 된다. 위험한 건 도구 하나가 아니라 **역량의 조합**이다. 허용목록(allowlist)도 여전히 유용하지만 안전의 증거는 아니다 — 자동 승인되는 경로가 있으면 공격자는 악의적 목적을 그 신뢰 경로로 통과시킬 동기를 갖는다.

테스트 방식도 바뀌어야 한다. 기능 테스트는 "작업이 완료됐는가"를 묻지만, 하이재킹된 에이전트는 중간에 악의적 행위를 하면서도 요청받은 작업을 완벽히 끝낼 수 있다. 따라서 결과만이 아니라 **경로를 검사**해야 한다 — 프롬프트 인젝션 테스트, 도구 호출 검사, 의심스러운 행동 시퀀스 탐지, 에이전트의 자기 보고와 독립된 모니터링, 접근 기록, 그리고 "같은 목표를 더 적은 권한으로 달성할 수 있었는가"라는 질문. 출력 테스트에서 결정과 행동의 테스트로 넘어간다는 것이다.

결론에서 저자는 에이전틱 AI가 방화벽을 무의미하게 만들지 않듯 모든 이전 시대는 다음 시대의 토대가 된다고 정리한다. 인프라 시대는 장비와 네트워크를, 클라우드 시대는 애플리케이션·분산 시스템·신원을 지키는 법을 가르쳤고, 에이전틱 AI 시대는 **의사결정 시스템을 지키는 법**을 요구한다. 그리고 클라우드 시대의 가장 중요한 교훈을 반복한다 — 직무명과 자격증과 교육과정이 새 시대의 도래를 알려주기를 기다리지 말 것. 그 시점이 오면 일찍 시작한 사람들은 이미 경험을 쌓은 뒤다.

**적용 각도(참고용 메모)**: ①비공개 데이터 ②비신뢰 입력 ③외부 채널 3요소 테스트는 우리 파이프라인에 그대로 적용된다 — 크롤링한 외부 콘텐츠(비신뢰 입력)를 읽고 블로그 레포에 push(외부 채널)하는 구조라 최소 하나를 구조적으로 끊는 설계 점검이 필요하며, 에이전트가 사람 자격증명을 빌려 쓰지 말라는 원칙은 gh 계정·SSH 키 운용 방식과 직결된다.
