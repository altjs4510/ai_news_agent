## 한글 요약

WWDC 26에서 키노트도 데모도 마케팅 예산도 못 받았지만 개발자에게는 가장 중요했던 발표를 정리한 글이다. 슬라이드도 거의 없이 작은 방에서 진행된 Session 389의 주제, **Container Machine** — macOS 26에서 네이티브로 도는 리눅스 환경이다. 1초 안에 부팅하고, 홈 디렉토리를 자동 마운트하고, 맥과 같은 사용자명을 쓰고, OCI 호환 이미지(도커 허브에서 받아본 모든 것)를 지원하며, 기본 운영체제에 오픈소스로 무료 탑재된다. 서버 코드 테스트용 리눅스 VM을 유지하거나, Docker Desktop에 돈을 내거나, Orbstack 라이선스와 씨름하거나, "리눅스 작업"만을 위해 낡은 우분투 노트북을 책상에 두던 개발자에게는 그 인프라가 통째로 불필요해졌다는 것이 저자의 주장이다. 멘탈 모델이 "VM을 돌리는 맥"이 아니라 **리눅스 개발 머신**으로 바뀐다.

**기반 — WWDC 25의 Containerization 프레임워크.** 2025년 6월 애플은 두 가지를 동시에 오픈소스화했다. Swift 프레임워크 Containerization(이미지 관리·컨테이너 실행·네트워킹·스토리지 API와 전부 Swift로 쓰인 리눅스 init 시스템)과 개발자용 래퍼인 `container` CLI(OCI 이미지를 받아 실행·관리하는 도커 모양의 명령줄)다.

여기서 모든 것을 가능하게 한 아키텍처 선택이 **컨테이너 하나당 경량 VM 하나**다. Docker Desktop과 Podman은 큰 리눅스 VM 하나를 띄우고 그 안에서 모든 컨테이너를 돌린다. 컨테이너들이 커널을 공유하고, 네트워크 인터페이스를 공유하며(그래서 `-p 8080:8080` 같은 포트 매핑이 필요하다), 파일시스템 마운트 표면도 공유한다. 애플의 `container`는 컨테이너마다 새 경량 리눅스 VM을 띄운다. 시작 시간은 1초 미만, **컨테이너마다 전용 IP를 받으므로 포트 매핑 없이 IP로 직접 접근**하고, 명시적으로 공유한 디렉토리만 격리 마운트된다. 컨테이너를 전부 멈추면 머신에 리눅스가 아예 돌지 않는다 — 자원을 먹는 백그라운드 데몬이 없다.

보안·프라이버시 함의가 구체적이다. 도커 모델에서는 컨테이너 하나가 침해되면 공유 VM 커널이 그 안의 모든 것에 대한 폭발 반경이 된다. 애플 모델에서는 각 컨테이너가 자기 VM에 있으므로 폭발 반경이 컨테이너 하나다. 마찬가지로 도커에서 호스트 디렉토리를 바인드하면 그 디렉토리가 먼저 공유 VM에 마운트돼 다른 컨테이너들이 볼 수 있는 상태가 되지만, 애플 모델에서는 대상 컨테이너의 VM에만 마운트된다. 각 경량 VM 안에서 PID 1로 도는 것은 **vminitd**라는 정적 링크 Swift 바이너리로, libc도 코어 유틸리티도 동적 라이브러리도 없다(musl 대상 Swift Static Linux SDK로 컴파일). 워크로드를 호스팅할 수 있는 최소한의 리눅스 유저스페이스만 남긴 것이다.

**중간 단계 — Container 1.0(2026년 6월 11일).** 2025년 6월 0.1에서 2026년 2월 0.8까지 20번의 포인트 릴리스를 거쳐 2026년 6월 초 1.0이 나왔다. 프로덕션 준비 완료, 표준 OCI 이미지 호환성 검증, 버그 급감, 성능 벤치마크는 대부분 지표에서 Docker Desktop·Orbstack과 비슷한 수준이고 메모리 처리량에서는 앞선다. 여기까지만 보면 애플이 더 빠른 도커를 만든 것 같지만, 실제로는 진짜 발표를 위한 토대였다는 게 저자의 정리다.

**Container Machine이 무엇인가.** 일반 컨테이너에는 없는 두 가지 속성을 부여받은 컨테이너다 — **영속성**과 **깊은 호스트 통합**. 애플 세션의 표현으로는 "컨테이너처럼 빠르고 가벼우면서 가상머신처럼 영속적이고, 호스트 통합까지 더해져 macOS에 네이티브처럼 느껴진다". 실제 의미를 풀면 이렇다.

- **영속성** — 화요일에 안에서 `apt install` 한 도구가 수요일에도 있다. 명시적으로 마운트한 볼륨 밖의 모든 것이 재시작 시 증발하는 일반 컨테이너와 다르다.
- **자동 사용자 매핑** — 컨테이너 안 사용자명이 맥 사용자명과 같고 UID/GID가 일치한다. 호스트/게스트 경계를 넘는 권한 모델이 그냥 동작한다.
- **자동 홈 디렉토리 공유** — 맥 홈 디렉토리가 **같은 경로로** 기본 마운트된다. 맥의 `~/projects/web-server`에서 편집한 파일이 컨테이너에서 `cargo build` 할 때 읽는 바로 그 파일이다. 동기화도, `docker cp`도, 볼륨 마운트 선언도 없다.
- **작업 디렉토리 상속** — 맥 터미널에서 어느 경로에 있든 `container machine run` 하면 리눅스 안 같은 경로로 떨어진다. "지금 컨테이너 안 어디지?"라는 인지 부하가 사라진다.
- **진짜 init 시스템** — systemd가 동작한다. postgres·redis·nginx를 감싼 프로세스가 아니라 제대로 된 시스템 서비스로 돌릴 수 있어, 로컬 시뮬레이션이 실제 배포 대상과 동일하게 동작한다.

WSL2를 써봤다면 비교가 적절하다고 저자는 인정한다 — 실행·보안 모델은 다르지만 개발자 경험의 목표는 같다.

**실사용 절차.** 설치는 `brew install container` 하나면 되고(GitHub 릴리스에서 패키지를 직접 받아도 된다), `container`와 `container machine`은 같은 CLI의 서브커맨드라 별도 설치가 없다. 첫 머신은 `container machine create --name dev --default alpine:latest` 로 만든다 — 이미지를 받고, 머신을 만들고, `--default`로 기본 지정해 매 명령마다 이름을 안 써도 되게 한다. `container machine list`로 IP·CPU 할당(기본 7개)·메모리 할당(기본 시스템 RAM의 절반)을 확인한다. `container machine run uname -a`는 `Linux ... GNU/Linux`를 출력하고, 맥 터미널에서 같은 명령은 `Darwin`을 출력한다 — 커널 둘, 워크플로 하나. 인자 없이 `container machine run` 하면 시작한 작업 디렉토리 그대로 리눅스 셸에 들어간다.

실제 작업용으로는 Ubuntu 24.04 기반 Dockerfile(build-essential·git·curl·vim·systemd 등을 넣고 `CMD ["/sbin/init"]`로 진짜 init을 띄우는)을 `container build`로 만든 뒤 그것으로 머신을 생성한다. 이후 설치하는 nodejs·postgres·redis·언어 툴체인은 재부팅을 넘어 유지된다.

**커뮤니티가 가장 많이 지적한 함정과 해법**이 실무적으로 유용하다. 맥 쪽에서 편집하고 리눅스 쪽에서 실행할 때 VS Code 핫 리로드와 디버그 브레이크포인트가 깔끔하게 동작하지 않는다 — 파일시스템 브리지는 견고하지만 **파일 감시 이벤트가 전파되지 않기** 때문이다. 해결은 애플 자체 문서에 있고 2분이면 된다: 호스트 마운트를 통해 편집하지 말고 **SSH로 컨테이너 머신에 붙어서** 편집하라. `container machine list`로 IP를 얻어 `ssh <사용자명>@<IP>`로 들어가고, VS Code에서 Remote-SSH 확장으로 그 IP를 가리키면 핫 리로드·브레이크포인트·파일 워처가 전부 작동한다. 저자는 이 한 수가 Container Machine을 "테스트용으로 훌륭"에서 "매일 쓰기에 훌륭"으로 바꾼다고 본다.

서비스 스택도 단일 머신 안에서 systemd로 관리한다 — `sudo apt-get install -y postgresql redis-server` 후 `sudo systemctl enable --now postgresql redis-server`. 진짜 init이 있으니 `systemctl`이 기대대로 동작하고, 서비스들이 머신 재시작을 넘어 살아남으며, 실제 리눅스 서버의 서비스처럼 행동한다. 맥 사파리에서 `http://<IP>:<포트>`로 열면 원격 리눅스 서버에 붙는 것과 같은데, 1초 안에 부팅하고 홈 디렉토리를 공유한다. 머신을 여러 개 병행할 수도 있어(Ubuntu·Alpine·Fedora 동시 운영) `--machine` 으로 지정해 명령을 보내면 **크로스 디스트로 테스트가 터미널을 떠나지 않고 가능**하다 — 우분투 머신에서 컴파일한 바이너리를 알파인 머신에서 곧바로 시험하는 식이다.

**아직 안 되는 것.** Docker Compose 등가물은 container 1.0에도 없다. 서드파티 래퍼 최소 세 개가 개발 중이지만 Docker Compose 수준의 완성도에 이른 것은 없고, 당분간의 현실적 대안은 systemd로 서비스를 관리하는 단일 컨테이너 머신으로 다중 서비스 워크로드를 돌리는 것이다. 저자는 이 공백이 몇 년이 아니라 몇 달의 문제라고 본다.

**반드시 알아야 할 함정 세 가지.** ① **메모리가 반환되지 않는다.** 기본 할당이 시스템 RAM의 절반인데 유휴 상태에서 macOS에 돌려주지 않는다. 빌드 중 메모리가 치솟으면 머신을 재시작할 때까지 붙잡고 있다. Orbstack의 동적 메모리 반환은 가장 사랑받는 기능인데 애플은 아직 못 따라왔다 — 16GB 맥에서 머신 3개를 만들면 8GB 할당 문제가 생기므로 생성 시 `--memory 4g`로 상한을 명시하라. ② **GPU·USB 패스스루가 아직 없다.** CUDA, GPU 가속 ML 추론, 리눅스 안에서의 USB 장치 접근이 필요하면 아직 이 도구가 아니다(둘 다 이슈가 열려 있다). ③ **홈 디렉토리 마운트가 기본 읽기·쓰기라는 보안 노출.** 맥 홈 전체를 리눅스에 마운트하는 편의는, 그 안에서 도는 무엇이든 — 악성 npm 패키지나 침해된 이미지 포함 — SSH 키, `~/.aws/credentials`, 사실상 전부를 읽을 수 있다는 뜻이다. `--home-mount readonly`로 읽기 전용으로 바꾸거나 `--home-mount none`으로 끌 수 있고, **신뢰할 수 없는 코드를 돌릴 머신이라면 반드시 이렇게 하라**는 것이 저자의 권고다. 폴더 단위 마운트 세분화는 아직 없다.

생산성 측면 정리 — Docker Desktop 오버헤드 제거(기본 RAM 2~4GB 회수), 호스트 디렉토리가 곧 컨테이너 디렉토리라 파일 위치 혼동 없음, 머신마다 IP가 있어 로컬 개발에서 포트 매핑 불필요, 진짜 systemd로 서비스 수준 로컬 테스트(테스트하는 것이 곧 배포하는 것), 터미널을 떠나지 않는 크로스 디스트로 테스트, SSH 경유 에디터 핫 리로드(최초 1회 설정), 1초 미만 콜드 스타트라 일회성 실험용 머신을 부담 없이 생성.

마지막으로 저자는 애플의 의도를 읽는다. 애플은 컨테이너를 도커에 맡길 수도 있었고 Orbstack 위에 세련된 UX를 얹고 끝낼 수도 있었지만, Swift로 직접 만들고 애플 실리콘에 최적화하고 기존 플레이어들을 넘어서는 보안 모델을 넣었다. 겨냥하는 대상은 **진지한 서버사이드 작업을 위해 리눅스 노트북으로 돌아가고 있던 개발자층** — Framework 노트북 사용자들, "CI를 위해 진짜 리눅스가 필요하다"는 사람들, "Docker Desktop은 너무 무겁다"는 사람들이다. 이들을 맥에 붙잡아 두려고 WWDC 두 번 분량의 엔지니어링 자본을 쓸 의향이 있었다는 것이고, 성능은 경쟁력 있고 아키텍처는 대안들보다 안전하며 통합은 윈도우의 WSL보다 긴밀하고 가격은 0이라는 점에서 저자는 그 시도가 통하고 있다고 평가한다.

**적용 각도(참고용 메모)**: "컨테이너당 VM 하나 → 폭발 반경이 컨테이너 하나"라는 격리 모델과 홈 마운트 기본 읽기·쓰기의 위험 경고는, 신뢰할 수 없는 코드를 로컬에서 돌릴 때(예: 외부 스크립트·에이전트 실행) 참고할 만한 기준선.
