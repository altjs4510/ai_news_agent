## 한글 요약

2026년 7월 들어 에이전트 개발 판에서 "그래프 엔지니어링(Graph Engineering)"이라는 말이 빠르게 번졌다. 발단은 OpenClaw 의 Peter Steinberger 가 올린 짧은 글 — "우리 아직도 루프 얘기를 하고 있나, 아니면 이미 그래프로 넘어갔나"는 취지의 문제 제기였다. 불과 몇 주 전까지 화제였던 건 "루프 엔지니어링"이었다. 사람이 매번 좋은 프롬프트를 넣어 주는 대신, AI 가 스스로 발견하고 실행하고 검증하고 기록한 뒤 다음 작업으로 넘어가는 반복 시스템을 설계하자는 것.

문제는 그 루프를 여러 번 돌려 보니 새로운 한계가 드러났다는 점이다. 저자의 진단은 "에이전트가 덜 똑똑해서"가 아니라 "조직 구조가 불분명해서"다. 에이전트 하나가 하나의 작업을 반복하는 건 잘 된다. 그런데 작업이 제품·아키텍처·데이터·보안·테스트·릴리스·비용·컴플라이언스에 걸쳐 있으면, 진짜 과제는 "에이전트가 몇 번 더 시도하게 만드는 것"이 아니라 "경계가 나뉜 여러 에이전트를 관측 가능하고 감사 가능하며 복구 가능한 방식으로 협업시키는 것"으로 바뀐다.

저자는 그래프 엔지니어링이 새로운 걸 발명한 게 아니라고 못 박는다. 작업을 어떻게 쪼갤 것인가, 의존 관계를 어떻게 표현할 것인가, 무엇을 병렬화할 수 있는가, 실패를 어떻게 복구할 것인가, 상태를 어디에 둘 것인가 — 에이전트 오케스트레이션의 해묵은 난제들에 새 이름을 붙였을 뿐이라는 것이다.

루프와 그래프의 차이는 "경로를 누가 설계하느냐"로 정리된다. 루프에서 사람이 정하는 건 목적과 통과 기준 두 가지뿐이고, 거기까지 가는 구체적 단계는 AI 에게 맡긴다. 기사 작성을 예로 들면 AI 가 초안을 쓰고 스스로 평가하고 약한 부분을 다시 쓰기를 기준 충족까지 반복한다. 반면 그래프에서는 사람이 목적·통과 기준에 더해 작업이 흘러갈 전체 경로까지 설계한다. 품질 평가가 기준 미달이면 집필 단계로 되돌리고, 글의 방향 자체가 틀렸으면 구조 설계와 리서치 단계까지 거슬러 올라가며, 승인되지 않은 문서는 발행 단계로 넘어갈 수 없다. AI 가 자유롭게 헤매는 게 아니라 미리 그려 둔 지도 안에서 움직인다.

저자는 이를 3계층으로 요약한다. **프롬프트 엔지니어링은 단일 모델 호출을 신뢰할 수 있게 만들고, 루프 엔지니어링은 한 에이전트의 행동을 신뢰할 수 있게 만들며, 그래프 엔지니어링은 에이전트 집단의 협업을 신뢰할 수 있게 만든다.** 각 계층의 핵심 대상도 다르다. 프롬프트의 대상은 지시문(모델이 무엇을 보는가, 어떤 형식으로 출력하는가, 무엇을 하면 안 되는가), 루프의 대상은 제어 사이클(트리거 조건, 도구 호출, 상태 갱신, 검증기, 재시도 전략, 정지 조건), 그래프의 대상은 토폴로지(노드, 엣지, 상태, 산출물, 권한, 관측, 평가, 변경 이력)다.

중요한 건 이 셋이 서로를 대체하지 않는다는 점이다. 그래프는 루프의 업그레이드판 래퍼가 아니고, 그래프가 도입됐다고 루프가 사라지지도 않는다. 더 정확히는 **각 주요 노드 안에 여전히 루프가 들어 있고, 그래프는 그 루프들을 어떻게 조직·제약·연결할지를 정한다.**

선택 기준도 명확하다. "매일 저장소 이슈를 스캔해 가장 단순한 버그를 고치고 테스트를 돌린 뒤 PR 을 연다" 정도의 명확한 루프면 루프로 충분하고, 그래프를 일찍 도입하면 복잡도만 늘어난다. 반대로 "API 호환성을 유지하면서 결제 시스템을 재구축하고, 데이터를 마이그레이션하고, 프론트엔드를 갱신하고, 테스트를 마치고, 보안 리스크를 평가하고, 릴리스 안내를 생성한다"처럼 본질적으로 도메인을 가로지르는 작업은 단일 루프로는 엉망이 된다. 이때 모델링해야 할 것은 "에이전트가 다음에 뭘 할까"가 아니라 데이터 노드가 어떤 마이그레이션 증거를 내놓는가, API 노드가 호환성을 어떻게 선언하는가, 프론트엔드 노드는 언제 병렬로 돌 수 있는가, 리뷰 노드는 어떤 산출물을 검사하는가, 릴리스 노드는 어떤 선행 조건을 기다려야 하는가 — 이미 그래프 문제다.

그래프가 유용해지는 지점을 저자는 기존 표 형태 데이터와 대비해 설명한다. 행과 열로 정리하는 방식은 집계와 정형 처리에는 매우 강력하지만, "이 사람과 간접적으로 연결된 사람은 누구인가", "부정 거래로 이어지는 공통 패턴이 있는가", "어떤 장애의 영향이 어디까지 퍼지는가", "여러 문서에 흩어진 정보들이 어떻게 연결되는가", "이 작업이 실패하면 어느 단계로 돌아가야 하는가" 같은 질문 앞에서는 무력하다. 이건 단일 데이터 포인트를 보는 문제가 아니라 여러 객체를 추적하며 그 관계의 의미를 캐는 문제다. 에이전트가 늘어날수록 이 관계의 중요성은 더 커진다 — AI 에게 정보를 많이 밀어 넣는다고 올바른 판단이 나오지 않기 때문이다. "어떤 정보가 어떤 정보에 근거하는가", "누가 승인했고 어떤 단계를 거쳤는가", "실패하면 어디로 되돌아가는가"를 구조로 명시해 두면 AI 의 판단을 통제하기 쉬워진다.

동시에 저자는 전부 그래프로 만들지 말라고 경계한다. 새 개념이 나오면 모든 곳에 적용하고 싶어지지만 그래프가 복잡성을 공짜로 해결해 주지는 않는다. 저자는 OpenAI 의 에이전트 구축 가이드도 선언적 그래프가 분기와 루프를 시각화해 주기는 하지만 동적 워크플로에서는 거추장스러워져 전용 기술 방식이 필요해진다고 지적하며, 그 대안으로 OpenAI Agents SDK 가 코드 중심의 유연한 아키텍처를 택했다고 소개한다. 목표가 하나이고, 도구를 거의 안 쓰고, 분기가 거의 없고, 중간 재개가 필요 없고, 실패하면 같은 자리로 되돌아가면 되고, 사람이 짧은 시간에 검증할 수 있는 작업 — 이런 건 단순 루프로 처리한다. 여러 부서·여러 에이전트·긴 실행 시간·병렬 처리·승인·감사가 필요해질 때 그래프가 값을 한다. 그래프 엔지니어링은 복잡한 다이어그램을 그리는 일이 아니라, 필요한 관계만 명확히 드러내고 불필요한 자동화는 버리는 설계다.

구현 사례로는 LangChain 팀이 만든 **LangGraph** 를 든다. 핵심 추상은 Node·Edge·State 셋. 예제 코드는 작업 이해(understand) → 정보 검색(retrieve) → 생성(generate) → 품질 평가(judge) 노드를 잇고, judge 결과에 따라 종료할지 retrieve 로 되돌릴지 정하는 조건부 엣지를 붙이는 구조다. 저자가 짚는 설계 포인트는 넷이다. ① 전역 상태가 그래프의 중심 — 모든 노드가 같은 상태 객체를 공유하고 노드의 입출력은 그 상태를 읽고 쓰는 것이라, 노드 간 데이터 전달 문제가 이걸로 해결된다. ② 분기는 `add_conditional_edges` 로 구현 — 현재 상태를 보고 다음 노드 이름을 반환하는 함수를 받는데, 이게 곧 FSM 의 상태 전이 조건이다. ③ 루프는 조건부 엣지로 만든다 — judge 에서 retrieve 로 돌아가는 되돌림 엣지(back edge)가 루프를 형성한다. ④ 종료 조건(예제에서는 재시도 3회 상한)은 명시적이고 강제적이어야 한다 — 악순환을 막기 위한 필수 설계이지 선택이 아니다.

저자는 결론에서 솔직하게 물러선다. 용어가 나온 지 사흘밖에 안 됐고 "그래프 엔지니어링"이라는 말이 살아남을지는 아무도 모른다는 것. 다만 그 밑에 깔린 개념 — 작업을 나누고, 병렬로 돌리고, 판단 체크포인트를 넣는 것 — 은 이름보다 오래 살아남았고 본인 경험상 효과를 확인했다고 말한다. 한 달 뒤 용어가 사라져도 글의 후반부는 여전히 쓸모 있을 거라는 게 집필 의도라고 덧붙인다.

**적용 각도(참고용 메모)**: ai_news_agent 의 daily/weekly 파이프라인은 크롤→요약→발행이 사실상 고정 경로인 얕은 그래프라 지금 구조로 충분하지만, 소스별 수집 실패 시 어디로 되돌아갈지·어떤 산출물이 있어야 다음 단계로 넘어갈 수 있는지를 명시적 상태로 두는 발상은 현재 main.py 의 "키 없으면 소스만 스킵" 식 가드를 정리할 때 참고할 만하다. 종료 조건을 강제 설계하라는 지적은 LLM 재시도/폴백(claude -p → LiteLLM) 경로에도 그대로 적용된다.
