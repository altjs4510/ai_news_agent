## 한글 요약

아키텍처 워크숍에서 누군가 "지식그래프 하나 만들죠"라고 던지면 다들 고개를 끄덕이지만, 사실 그 자리에서 서로 다른 세 개념이 하나로 뭉개진다는 게 이 글의 문제의식이다. 표준 데이터 모델(CDM)·온톨로지·지식그래프는 각각 다른 문제를 푸는 층인데, 이걸 합쳐버리면 과설계와 "모든 걸 하려다 아무것도 제대로 못 하는" 시스템이 나온다.

저자가 반복해서 봤다는 전형적 전개는 이렇다. 시스템 간 데이터 포맷이 안 맞는 평범한 통합 문제로 시작 → 표준 데이터 모델을 만들자(좋은 생각) → 이왕이면 모든 것의 *의미*도 정의하자(이것도 좋은 생각) → 그럼 지식그래프로 다 해결하자(여기서 탈선). 이 순간 **구조·의미·데이터** 세 층이 하나로 붕괴하고 복잡도가 새어 들어온다.

**CDM 은 번역기다.** 깊은 의미를 다루지 않고 추론도 하지 않는다. 서로 다른 데이터 모델과 포맷을 하나의 합의된 구조로 바꾸는 것, 그게 전부다. 이 패턴이 중요한 실용적 이유는 조합 폭발이다. N 개 시스템을 점대점으로 이으면 대략 N×(N−1) 개의 변환을 유지해야 하지만, 공통 포맷 하나를 경유하면 N 개 매핑으로 줄어든다. 저자는 이를 엔터프라이즈 통합 패턴의 고전적 논거로 언급한다. 구현은 보통 JSON Schema·XSD·Avro·Protobuf 같은 스키마/직렬화 표준이나 표준 메시지 포맷으로 이뤄진다. 비유하자면 이중언어 사전 — 단어의 철학이나 어원을 설명하지 않고 그냥 번역만 해준다. 공통 포맷이 없으면 API 가 깨지고 파이프라인이 실패하니 강력하지만, CDM 만으로는 그 데이터가 *무엇을 뜻하는지* 알 수 없다.

**온톨로지는 규칙집이다.** 페이로드나 API 스키마를 정의하는 통상적 의미의 데이터 모델이 아니라, 개념(고객·제품·주문)과 관계(고객이 제품을 구매한다), 그리고 제약(주문은 반드시 하나의 고객에 속한다)을 형식적으로 기술한다. 저자는 이를 "공유된 개념화에 대한 형식적·명시적 명세"라는 고전적 정의에 연결하고, 실무 표현 수단으로 RDFS·OWL·SKOS 를 든다. 중요한 구분은 의미/규칙(용어 층)과 개별 사실의 주장(인스턴스 층)이 **역할상** 나뉜다는 점 — 다만 이 분리는 논리적인 것이지 물리적 강제가 아니어서, 둘이 같은 그래프 저장소에 살고 같은 인터페이스로 질의되는 경우가 흔하다. 이 층을 건너뛰면 팀은 의미를 데이터 포맷이나 비즈니스 로직에 하드코딩하게 되고 거기서 불일치가 자란다. 반대로 상상 가능한 모든 엣지케이스를 모델링하려다 과설계로 가기도 하는데, 저자는 "이걸 모델링하지 않으면 무슨 일이 벌어지나?"라고 자문해보라고 권한다. 답이 "별일 없다"면 단순하게 가라는 신호다.

**지식그래프는 실제 사실이 사는 곳이다.** 추상적 정의나 스키마가 아니라 "이 사람은 고객이다", "이 사람이 제품 X 를 샀다" 같은 현재 상태에 대한 진술의 네트워크다. 온톨로지가 *무엇이 존재할 수 있는가*를 정하면 지식그래프는 *지금 실제로 무엇이 존재하는가*를 담는다. 이해 가능하고 거버넌스 가능한 상태를 유지하려면 대개 온톨로지나 최소한 공유 스키마에 기대야 한다. 그 밑받침이 없으면 그저 "연결된 데이터"일 뿐이고, 있어야 비로소 추론과 도메인 간 연결이 가능해진다. 그리고 지식그래프는 데이터 교환을 자동으로 해결해주지도, API 를 대체하지도, 데이터를 마법처럼 정제해주지도 않는다.

흔히 나오는 오해 네 가지를 저자는 이렇게 정리한다. "우리 지식그래프가 곧 데이터 모델이다" — 아니다, 셋은 각각 사실·구조·의미를 담당하며 섞으면 바꾸기도 설명하기도 어려워진다. "온톨로지를 CDM 안에 정의하자" — 구조와 의미를 묶으면 결합도가 올라가고 유연성이 죽는다. "온톨로지는 됐고 그냥 그래프 쓰자" — 도시를 용도지구 규칙 없이 짓는 격이라 나중에 데이터를 해석하는 게 추측 게임이 된다. "일단 다 미리 모델링하자" — 아직 존재하지 않는 문제를 풀면서 새 문제를 만든다.

정상적으로는 세 층이 이렇게 맞물린다. 온톨로지로 의미를 정의하고 → 지식그래프에 실제 상태를 담고 → CDM 으로 예측 가능한 포맷으로 내보낸다. 한 줄로는 온톨로지 = "이게 무슨 뜻인가", 지식그래프 = "실제 상태는 무엇인가", CDM = "어떤 형식으로 주고받나". 다만 셋 다 필요한 경우는 오히려 드물다 — 잘 만든 관계형 DB 로 충분할 때도, CDM 만으로 될 때도, 가벼운 용어 합의만으로 될 때도 있다. 층을 하나 더 얹을 때마다 설계 노력·정렬 논의·거버넌스 비용이 따라온다.

마무리 논지가 지금 이 구분이 중요해진 이유다. 생성형 AI·RAG·에이전트 시스템이 들어오면서 이건 더 이상 이론적 구분이 아니다. 데이터가 얼마나 잘 이해되는지, 시스템이 얼마나 신뢰성 있게 추론할 수 있는지에 직접 영향을 준다. 온톨로지 없는 지식그래프는 신뢰하기 어렵고, 데이터 없는 온톨로지는 쓸모가 없고, 공유된 의미 없는 CDM 은 해석이 안 된다. 다음에 누가 "지식그래프 만들죠"라고 하면 잠깐 멈추고 물으라는 게 저자의 제안이다 — 우리가 지금 말하는 게 구조인가, 의미인가, 실제 데이터인가?

**적용 각도(참고용 메모)**: DCS AI 지식그래프(KG) 논의에서 "KG 로 조회한다"는 말이 실제로는 세 층 중 무엇을 가리키는지 구분해두면 요청 라우팅이 명확해진다 — 정식 API 로 사실을 꺼내는 층(KG), 지표·용어 정의 층(온톨로지), 결과를 앱·대시보드로 넘기는 교환 포맷 층(CDM)은 각각 다른 사람이 오너다.
