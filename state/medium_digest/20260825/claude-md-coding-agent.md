## 한글 요약

코딩 에이전트는 커피 한 잔 마실 새 수백 줄을 쓰지만, 그중 상당수는 "자신 있게 틀린" 코드다 — 컴파일도 되고 그럴싸하게 읽히지만 세 함수 전에 잘못된 가정을 조용히 깔고 간다는 문제의식에서 출발.

필자는 처음엔 "규칙 적어놓은 마크다운 파일 하나로 뭐가 달라지겠냐"며 회의적이었지만, 직접 CLAUDE.md를 만들어 쓴 뒤 QuaRot(피어리뷰 통과한 양자화 알고리즘)을 실제로 능가하는 양자화 기법(ApexQuant)을 주말 만에, 버그도 거의 없이 구현하는 데 성공했다.

**핵심 프레임**: Karpathy의 비유대로 모델을 CPU, 컨텍스트 윈도우를 RAM으로 보면 — 세션 간 기억이 없는 에이전트는 지금 로드된 것만 갖고 움직인다. 그래서 잘하는 프롬프트 한 줄보다, 매 세션 시작 시 읽히는 "상시 규정" 파일(CLAUDE.md)이 훨씬 durable한 컨텍스트 엔지니어링이다.

**CLAUDE.md의 4대 행동 규칙**:
1. **코딩 전에 생각하기** — 가정을 소리 내어 말하고, 모호하면 임의로 하나 골라 200줄 쓰지 말고 되물을 것.
2. **단순함 우선** — 한 번만 쓰이는 코드에 추상화 금지, 발생 불가능한 케이스에 에러 핸들링 금지. "시니어가 봤을 때 과하다 싶으면 잘라내라"가 기준.
3. **수술적 변경** — 요청받은 부분만 건드리고, 옆 코드 "개선"하거나 스타일 바꾸지 않기. 3줄 수정이 600줄 diff가 되는 걸 막음.
4. **목표 지향 실행** — "검증 없이는 안 됨"으로 모든 작업을 변환. "버그 고쳐줘" → "재현 테스트 작성 → 통과시키기".

**진짜 엔진은 하네스(harness)**: 테스트/린트/타입체커 등 pass/fail을 판정하는 외부 장치. "방을 편안하게 해줘"(모호한 지시) 대신 "21도로 유지해줘"(검증 가능한 지시)로 바꾸면, 사람 개입 없이도 빌드→체크→수정→재실행 루프를 돌릴 수 있다. 단, 판단이 필요한 작업(디자인 결정, 긴 학습 실행)에는 루프를 걸지 말 것 — 반복 횟수 상한과 git 브랜치 분리도 필수.

**출처(gstack)**: Y Combinator CEO Garry Tan이 오픈소스로 공개한 Claude Code 셋업. "얇은 하네스, 두꺼운 스킬" 철학으로 슬래시 커맨드 역할 분담(생각→계획→빌드→리뷰→테스트→배포→회고). 100k+ GitHub 스타를 단기간에 받음. 비판(그냥 텍스트 파일 모음 아니냐)도 있지만, "그냥 텍스트 파일"이 모델 행동에 미치는 영향을 저평가하는 비판이라는 게 필자 입장.

**실증 사례(ApexQuant)**: 신경망 가중치를 저비트로 양자화할 때 이상치(outlier)가 문제인데, QuaRot은 랜덤 회전으로 이상치를 분산시켜 균일 그리드로 양자화. ApexQuant는 한 걸음 더 나가 실제 가중치 분포(베타분포 형태)에 맞춰 양자화 레벨을 배치 — row가 긴(수백 개) 레이어에서 큰 우위, row가 짧은(모바일 depthwise 등 9개 수준) 레이어에서는 QuaRot과 동률이거나 열세. 그래서 레이어별로 GOOD/MARGINAL/BAD를 사전 감사하는 기능을 함께 배포.

**필자가 인정하는 한계**: 마법 아님(사소한 작업엔 그냥 오버헤드), 아이디어 자체를 대신 내주지 않음(설계·실험은 여전히 사람 몫), 하네스 섹션은 기본적으로 비어있어 각자 채워야 함(안 채우면 매너만 남고 엔진이 없는 셈), 판단 필요한 작업에 루프 걸면 돈·시간만 태움.

**적용 각도(참고용 메모)**: `applied-learning` 판단은 별도로 하되 — CLAUDE.md의 "4규칙 + 하네스 루프" 구조는 hermes/ai_news_agent 등 우리 프로젝트 CLAUDE.md 작성 관행과 직접 비교해볼 만한 프레임.
