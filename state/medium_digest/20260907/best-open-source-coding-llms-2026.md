## 한글 요약

2026년 오픈소스 코딩 모델이 프런티어를 따라잡았다는 관찰에서 출발하는 지형도 글이다. DeepSeek V4 Pro가 SWE-bench Verified에서 80.6%로 보고되며 세계에서 가장 비싼 폐쇄형 모델들 옆자리에 앉았다. 다만 함정이 있다 — 지금 가장 좋은 오픈 코딩 모델은 당신에게 없는 서버 랙을 요구하고, 24GB 그래픽카드 한 장에서 도는 모델은 전혀 다른 모델인데도 정상에 놀랄 만큼 가깝다. 필자는 그래서 질문을 바꾼다. "전체에서 무엇이 가장 좋은가"가 아니라 **"내가 실제로 하는 코딩에, 내가 돌릴 수 있는 것 중에 무엇이 가장 좋은가"**다.

### 1군: 빌려 쓰는 프런티어 6종

폐쇄형 프런티어와 주고받는 급으로, 4000억에서 3조에 가까운 파라미터 범위다. 자기 하드웨어에 올리기보다 API로 부르게 될 가능성이 높으며, AI 랩들 간 가격 전쟁 덕분에 폐쇄형 API의 일부 비용으로 빌릴 수 있다. 이 계층에서 오픈소스의 의미는 **벤더 락인 없는 싸고 교체 가능한 API 엔드포인트**다.

**GLM-5.2 (Zhipu)** — 대형 저장소를 가로지르는 길고 다단계적인 엔지니어링 과업을 겨냥해 만들어졌고, 100만 토큰 컨텍스트 전반에서 초점과 변수 의존성을 추적한다. MIT 라이선스, 총 7530억 파라미터 규모의 MoE로 토큰당 약 400억만 활성화한다. 더 어려운 SWE-bench Pro에서 62.1%로 오픈 진영 1위. API 가격은 100만 토큰당 입력 약 $1.40, 출력 $4.40. 필자는 100만 토큰 컨텍스트를 다루는 데 특정한 아키텍처 트레이드오프가 든다고 짚는다 — 컨텍스트가 길어지면 어텐션이 흔히 '건초더미 속 바늘' 열화를 겪어 프롬프트 중간에 묻힌 사실을 무시하는데, GLM-5.2는 수정된 RoPE 스케일링으로 중간 구간 회상을 이전 세대보다 잘 보존한다. 저장소 전체의 AST를 프롬프트에 붙여 넣으면 모델이 실제로 그걸 쓴다는 것.

**Kimi K2.7 Code (Moonshot AI)** — 자율 동작을 염두에 두고 설계됐다. 백그라운드 워커의 경쟁 상태를 기술한 GitHub 이슈를 가리키면, 수정을 작성하고 테스트 스위트를 돌리고 실패 로그를 읽고 테스트가 통과할 때까지 함수를 다시 쓴다. 모델 카드에 따르면 하나의 복잡한 요청을 처리하며 수백 개의 하위 에이전트로 수천 단계를 조율한다. 총 1조 파라미터에 토큰당 320억 활성화, 수정된 MIT 라이선스. 컴파일러나 린터와 반복적으로 상호작용해야 하는 사내 코딩 에이전트를 만든다면 필요한 도구 사용 신뢰성을 제공한다. 이 에이전트적 신뢰성의 출처는 사후 학습 방식이다 — 표준 인스트럭션 튜닝 대신 성공·실패한 컴파일러 출력 궤적에 대해 광범위한 강화학습을 거쳤고, 그래서 문법 오류를 실패 상태가 아니라 직전 출력을 조정하라는 신호로 이해한다.

**DeepSeek V4 Pro / Flash** — 자기 서버를 돌릴 전기값보다 API 경로가 싸지는 지점을 만든다. 로그·문서·코드 수백만 토큰을 몇 센트에 처리할 수 있어 대량 문서 생성과 CI/CD 파이프라인 분석의 기본 선택지가 된다. Pro·Flash 모두 MIT 라이선스에 100만 토큰 컨텍스트. Pro는 100만 토큰당 입력 약 $0.435 / 출력 $0.87, Flash는 $0.14 / $0.28로 떨어진다. 자동화 워크플로 통합은 OpenAI SDK 기본 코드에서 base URL과 모델 ID만 바꾸면 되는 수준이라고 예시 코드를 붙인다.

**Qwen3-Coder-480B-A35B (Alibaba)** — Apache 2.0 라이선스의 480B MoE. 25만 6천 토큰을 다루고 SWE-bench Verified 69.6%. 필자가 강조하는 건 성능보다 라이선스다 — 많은 오픈 웨이트 모델이 상업적 사용을 제한하거나 일정 매출 이상에서 보고를 요구하는 커스텀 라이선스를 쓰는데, Apache 2.0은 그 마찰을 없앤다. 법무 검토 없이 상업 출시가 가능하다는 것. 상용 코딩 제품을 만들면서 보안이 요구되는 엔터프라이즈 환경에 합법적으로 자체 호스팅할 프런티어급 백엔드가 필요하다면 가장 안전한 선택이다. 다만 배포 부담이 크다 — 8비트 양자화에서도 0.5TB에 가까운 VRAM, 즉 H100 8장이나 MI300X 8장 노드가 필요하다. 토큰당 활성 350억 파라미터가 생성 지연은 낮게 유지하지만, 가중치를 담을 메모리 용량이 하드웨어 규모를 결정한다.

**MiniMax M3** — 시각적 맥락이 필요한 무거운 프런트엔드 워크플로를 겨냥한다. Figma 익스포트와 CSS 모듈, UI 버그 스크린샷을 함께 넣고 시각 참조에 맞게 flexbox 레이아웃을 엮어달라 할 수 있다. 네이티브 멀티모달 기능이 시각적 레이아웃을 고쳐야 할 React 컴포넌트로 직접 매핑한다. 100만 토큰 컨텍스트, SWE-bench Pro 59%, 상업적 사용이 제한된 커스텀 라이선스. 입력 100만 토큰당 약 $0.30이고 출력은 API 제공자 라우팅에 따라 대체로 $0.96~$2.40 사이라 멀티모달 과업에는 경제적이다.

**Kimi K3 (Moonshot)** — 2026년 7월 26일 오픈 웨이트를 공개하며 규모를 2조 8천억 파라미터로 밀어 올렸다. 100만 토큰 컨텍스트. 현 오픈 생태계의 역량 정점으로 복잡한 알고리즘 추론, 시스템 프로그래밍, 컴파일러 최적화를 다룬다. 다만 2.8T 규모 탓에 자체 호스팅이 가장 어렵고 대다수 개발자에게는 사실상 API 전용이다.

### 2군: 소유하는 4종

앞의 여섯은 빌리는 것이고, 이 넷은 갖는 것이다. 개인 개발자에게 오픈소스가 실제로 값을 하는 지점 — API 청구서가 없고, 독점 코드가 기기를 떠나지 않는다. 일상 코딩의 대부분에서는 프런티어와의 격차를 체감하지 못할 만큼 가깝다는 것이 필자의 평가다.

**Qwen3-Coder-Next** — 64GB나 96GB Mac Studio, 또는 128GB AMD Strix Halo를 가졌다면 목표로 삼을 모델. 총 80B에 SWE-bench Verified 70.6%, Apache 2.0. 4비트 양자화로 약 46GB 통합 메모리에서 돈다. 진짜 기술적 요령은 MoE 구조로, 토큰당 30억 파라미터만 활성화된다. 필자는 여기서 로컬 LLM 성능의 '조용한 살인자'가 메모리 대역폭이라고 설명한다 — 토큰을 생성할 때마다 활성 가중치를 메모리에서 연산 코어로 읽어야 하는데, 밀집 80B 모델은 단어 하나마다 800억 파라미터를 옮겨야 한다. 30억만 활성화하면 대역폭 요구가 줄어 Strix Halo 같은 소비자용 통합 메모리에서 초당 50토큰 이상이 나온다.

**Qwen3.6 27B** — 24GB 카드를 쓰는 1인 개발자용. Alibaba가 2026년 4월 Apache 2.0으로 공개한 밀집 모델이며 Q4 정밀도에서 약 17GB VRAM이라 RTX 3090·4090·5090 한 장에 넉넉히 들어간다. 밀집 27B로 훨씬 큰 아키텍처들과 겨룬다. 표준 텍스트·코딩 워크플로는 커뮤니티 GGUF로 Ollama에서 완벽하게 돌지만, 네이티브 멀티모달 비전 기능을 쓰려면 별도 mmproj 비전 파일이 필요하고 llama.cpp나 LM Studio로 서빙해야 한다(글에 `llama-server` 실행 예시가 붙어 있다).

**Devstral Small 2 (Mistral)** — 다중 파일·도구 사용 작업을 위해 만든 240억 밀집 모델, 25만 6천 토큰 컨텍스트, Q4에서 24GB 카드에 적합, Apache 2.0. 셸 명령을 실행해야 하는 파이썬 스크립트에 로컬 모델을 물릴 때 JSON 스키마 제약과 함수 시그니처를 안정적으로 지킨다. 에이전트 프레임워크에서 Qwen 계열 대신 쓸 대안이 필요할 때 좋은 다양성 카드라는 평가.

**gpt-oss (OpenAI)** — gpt-oss-20b는 총 210억에 36억 활성화, 약 14GB VRAM으로 16GB 카드에 맞는다. 더 큰 gpt-oss-120b는 80GB급 하드웨어가 필요하다. OpenAI 계보를 로컬 하드웨어로 가져온다는 의미가 있고, 코드를 쓰기 전에 문제를 추론하는 데 강해 복잡한 알고리즘의 논리를 내부 사고 흐름으로 풀어낸 뒤 최종 구현을 출력한다.

### 모두가 틀리는 하나: 자동완성

위 목록은 전부 채팅·에이전트 모델인데, 정작 개발자가 가장 자주 하는 작업에는 어느 것도 맞는 도구가 아니라는 지적이다. 탭 자동완성은 완전히 다른 접근을 요구한다 — **FIM(fill-in-the-middle)**이다. FIM은 커서 위와 아래 사이의 코드를 예측하도록 가르치는 별도의 학습 목표다. 표준 인과적 언어모델은 앞선 내용만 보고 다음 단어를 예측할 줄 알지만, FIM은 파일을 접두·접미·중간 구간으로 토큰화해 그 틈을 잇도록 훈련한다. 여기에 1조 파라미터 에이전트를 쓸 수는 없고, 에디터에 직접 물려 밀리초 단위로 토큰을 예측하는 작고 빠른 모델이 필요하다.

오픈 진영의 답은 **Codestral 2**로, Mistral이 2026년 4월 Apache 2.0에 네이티브 FIM 지원으로 내놨고 16~24GB VRAM이 든다. VS Code·JetBrains용 오픈소스 확장인 Continue.dev에 물리면 Copilot 탭 자동완성을 더 낮은 지연으로, 구독 없이 로컬에서 재현할 수 있다. 하드웨어가 더 작다면 Q4에서 약 9.5GB를 쓰는 Qwen2.5-Coder 14B가 대안이다. 설정에서는 역할을 `autocomplete`로 명시해야 에디터가 올바른 FIM 토큰으로 프롬프트를 구성한다(`~/.continue/config.yaml` 예시 포함).

### 하드웨어 기준선

로컬 배포의 어림셈은 **Q4 정밀도에서 파라미터 10억당 약 0.6GB VRAM**이다. 24GB 카드면 32B 모델에 넉넉한 컨텍스트 창까지 담긴다. 통합 메모리 구조는 다르게 작동해서, 64GB·96GB Mac Studio나 128GB AMD Strix Halo 박스는 원래라면 엔터프라이즈 GPU 여러 장짜리 전용 서버가 필요했을 모델을 돌린다.

필자의 마무리는 단순하다 — 하드웨어 제약과 자기 워크플로를 정의하고 나면 선택은 자연히 떨어진다. 메모리 용량에 맞는 항목을 찾아 오늘 밤 가중치를 받고, 알맞은 도구를 에디터에 바로 물리라는 것.

**적용 각도(참고용 메모)**: 사내망 전용 LiteLLM 프록시가 GitHub Actions 공용 러너에서 안 닿는 이 프로젝트의 미해결 과제에 대해, Apache 2.0 자체 호스팅 가능 모델(Qwen3-Coder 계열)이나 공용 도달 가능한 저가 API(DeepSeek V4 Flash)가 폴백 후보가 될 수 있다.
