## 한글 요약

프로덕션에서 테라바이트급 데이터를 처리하든 초당 1만 요청을 받든, 최적화는 결국 하드웨어 자원(특히 CPU)을 얼마나 효율적으로 쓰느냐로 수렴한다는 문제의식에서 출발한 정리 글이다. 필자는 멀티스레딩과 멀티프로세싱에 대한 자기 이해를 먼저 일반 개념으로 세우고, 그다음 데이터 엔지니어가 가장 많이 쓰는 파이썬 맥락에 얹는다.

**프로세스와 스레드.** 프로세스는 독립적으로 실행되는 프로그램이고, OS가 실행 시 자기 메모리 공간을 포함한 전용 자원 일습을 준다. 중요한 건 프로세스가 RAM을 직접 만지지 않는다는 점이다 — OS가 건네준 주소로만 일하고, 그 주소가 어떤 물리 메모리를 가리키는지는 OS가 정한다. 그래서 두 프로세스의 데이터가 RAM에서 바로 옆에 놓여 있어도 서로 접근할 수 없다. 대화하려면 파이프·소켓·공유 메모리 세그먼트·메시지 큐 같은 OS 중개 수단이 필요하고, 이게 프로세스 간 통신(IPC)이다. 보내는 쪽이 직렬화하고 받는 쪽이 역직렬화하는 비용이 매번 붙는다. 예외는 공유 메모리로, OS가 같은 물리 페이지를 양쪽 주소 공간에 매핑해 주기 때문에 직렬화가 없다 — 대신 경쟁 상태(race condition)를 막을 동기화 부담이 생긴다. 경쟁 상태란 두 주체가 같은 변수를 건드리는 순서에 결과가 좌우되는 상황으로, 한쪽이 다른 쪽 작업을 덮어쓰거나 절반만 갱신된 값을 읽게 된다.

스레드는 프로세스 안에 산다. 한 프로세스가 여러 스레드를 가질 수 있고, 이들은 힙과 전역 변수를 포함한 프로세스 자원을 공유한다. 그래서 스레드 간 공유는 프로세스 간 통신보다 오버헤드가 훨씬 적고, 생성 비용도 가볍다. 요약하면 프로세스는 격리와 안전(서로의 데이터를 볼 수 없음)을 주지만 만들고 대화하는 비용이 비싸고, 스레드는 싸고 빠르지만 기본적으로 안전하지 않아 락 같은 조율 장치가 필요하다.

**코어와 두 모델.** 코어는 CPU 안의 개별 처리 단위로 명령을 가져와 실제 계산을 하며, 한 시점에 하나의 스레드를 돌린다. 멀티프로세싱은 각자 메모리 공간을 가진 독립 프로세스 여러 개가 같은 문제의 다른 부분을 맡는 것이다. 공유 상태가 없으니 보호할 것도 없고, 코어만 충분하면 조율 없이 동시에 돈다. 대가는 통신 비용이며, 프로세스들이 서로 협력해야 할수록 그 비용이 커진다. 멀티스레딩은 한 프로세스 안에서 여러 스레드가 자원을 공유하며 도는 것이라 직렬화가 없는 대신, 조율 없는 동시 쓰기가 값을 망가뜨릴 수 있다. 멀티스레딩을 지원하는 모든 언어가 락·뮤텍스·세마포어를 제공하는 이유가 여기 있다 — "한 번에 한 스레드만 이걸 만진다"를 보장하고, 다음 스레드가 앞선 스레드가 쓴 값을 실제로 보도록 만드는 장치다. 전부 읽기 전용이면 문제없지만 수정이 끼면 경쟁 상태를 고려해야 한다.

**동시성과 병렬성.** 동시성은 여러 일이 겹치는 시간대에 진행되도록 일을 조직하는 방식으로, 특정 순간에 실제로 실행 중인 건 하나여도 된다. 병렬성은 형태는 같지만 "실행이 같은 시각에 일어나야 한다"는 엄격한 요구가 추가된다. 멀티프로세싱은 자원이 격리돼 있어 스케줄러가 별도 코어에 배치하는 걸 막을 게 없으니 병렬성을 더 쉽게 얻는다 — 다만 "더 쉽게"지 "정의상"은 아니다. 4코어 머신에서 16개 프로세스를 돌리면 어느 순간에도 12개는 코어를 기다린다. 멀티스레딩은 스레드 수와 코어 수에 따라 갈린다. 한 코어에 몰리면 동시적이기만 하고, 4개 코어에 흩어지면 병렬이 된다. OS 스케줄러가 시스템 전체의 실행 가능한 스레드를 보고 어느 스레드를 어느 코어에 올릴지 정하며, 스레드가 코어보다 많으면 일부는 같은 코어에서 번갈아 돌아 그 순간엔 일부만 진짜 병렬이 된다.

**GIL.** 표준 파이썬 인터프리터인 CPython에는 전역 인터프리터 락(GIL)이 있어 어느 순간에도 파이썬 바이트코드를 실행하는 스레드는 하나뿐이다 — 노트북에 코어가 몇 개 놀고 있든 무관하다. 스레드는 네트워크 호출이나 디스크 읽기처럼 인터프리터 바깥에서 뭔가를 기다리며 OS에 제어를 넘기는 순간 GIL을 놓는다. 참고로 GIL은 이제 선택 사항이 됐다 — PEP 703이 GIL 없는 별도 CPython 빌드를 추가했고 3.13에서 실험적, 3.14에서 공식 지원이다. 다만 별도 바이너리(python3.14t)라 명시적으로 골라 써야 하고, 이 글의 GIL 서술은 기본으로 받는 표준 빌드 기준이다.

**멀티스레딩이 언제 통하나.** 놓은 락을 받아갈 사람이 없으면 의미가 없다. 파일 다운로드를 기다리는 단일 스레드가 GIL을 놓아도 대기 중인 다른 스레드가 없으면 GIL이 애초에 없었던 것처럼 그냥 기다릴 뿐이다. 그래서 `threading` 모듈로 스레드를 더 투입한다 — `Thread(target=some_function)`으로 함수를 작업 단위로 감싸고 `start()`로 OS 스케줄러에 넘기면, 놓인 락을 다른 OS 스레드가 받아갈 수 있게 된다. 이 구조가 멀티스레딩이 I/O 바운드 작업에서는 평판을 얻고 CPU 바운드에서는 무너지는 이유를 설명한다. I/O 바운드 코드는 대부분의 시간을 바깥을 기다리며 보내는데 그 상태가 곧 GIL을 놓는 상태다. 반면 CPU 바운드 파이썬 코드는 기다릴 게 없어 락을 계속 쥔다. 예외는 NumPy처럼 무거운 작업을 C에서 처리하는 라이브러리로, 인터프리터가 필요 없으니 그동안 GIL을 놓는다.

**GIL이 있어도 경쟁 상태는 생긴다.** 스레드가 같은 순간에 바이트코드를 실행하지 못하니 안전하겠거니 하기 쉽지만, GIL이 보장하는 원자성은 바이트코드 명령 하나 수준이지 명령 여러 개의 묶음이 아니다. `counter += 1`은 원자적으로 보여도 내부적으로는 읽기·더하기·쓰기의 세 단계다. CPython은 I/O 때만이 아니라 계산 중인 스레드도 교체한다 — GIL을 원하는 스레드가 기다리다 스위치 간격(기본 5ms, `sys.getswitchinterval()`) 후 플래그를 세우면, 실행 중인 스레드가 바이트코드 명령 사이에서 그 플래그를 확인하고 넘겨준다. 그 확인 시점은 "읽기·더하기·쓰기가 한 묶음이어야 한다"는 사정을 모른다. 스레드 A가 카운터 0을 읽고 쓰기 전에 락을 B에게 넘기면, B가 `counter += 1`을 온전히 수행해 1로 만든다. 그 후 A가 낡은 0을 들고 재개해 1을 더해 1을 쓴다 — 증가가 두 번 일어났는데 결과는 2가 아니라 1이다.

필자는 파이썬 3.10에서 GIL 해제 방식에 최적화가 들어갔다는 점도 덧붙인다. 3.10 이전엔 사실상 아무 바이트코드 명령에서나 해제·획득이 일어날 수 있었지만, 이후로는 특정 명령에서만 일어나 모든 명령이 "해제 가능"하지는 않게 됐다. 위 예시의 읽기·증가·쓰기 명령들에는 해제 가능 명령이 없어서 `counter += 1`이 한 스레드에서 끝까지 수행될 수 있다. 다만 이건 이 특정 사례에 한한 얘기이며 `+=`가 일반적으로 경쟁 상태에서 안전하다는 뜻이 아니고, 적절한 동기화 없이 멀티스레딩 환경에서 경쟁 상태가 완전히 사라진다는 뜻도 아니라고 못박는다.

**Async와의 차이.** 비동기는 현재 작업이 끝나기를 기다리지 않고 다른 일을 처리하다가, 끝나면 알림을 받아 결과를 다루러 돌아오는 방식이다. 파일 다운로드와 간단한 계산 두 작업이 있을 때 I/O를 기다리는 동안 계산으로 건너뛴다. 멀티스레딩과 비슷해 보이지만 결정적 차이는 **일이 어디서 도느냐**다. 멀티스레딩은 OS 스레드를 여러 개 띄우고 OS가 그것들을 번갈아 돌리지만, async는 모든 작업을 단일 스레드에서 돌리고 컨텍스트 전환이 OS가 아니라 프로그램 안에서 일어난다. 작동 방식은 이렇다 — 작업마다 명시적 대기 지점(`await`)이 있지만 `await` 자체가 제어를 넘기는 게 아니라, 네트워크 호출·디스크 읽기·타이머처럼 실제로 작업을 중단시키는 대상을 기다릴 때만 제어가 시스템으로 돌아간다. 그 시스템은 모든 작업을 관리하는 단일 이벤트 루프로, 한 작업이 중단될 때까지 돌리고 다음으로 넘어간다. 대기 중에도 이벤트 루프는 놀지 않고 어떤 작업이 준비됐는지 지켜보다 멈춘 지점에서 정확히 재개시킨다. 모두 한 스레드에서 도니 락 경합이 없고 — 뒤집어 말하면 한 작업의 블로킹 호출이 전체를 멈춰 세운다. 정리하면 멀티스레딩은 OS 수준의 진짜 동시성을 OS 수준 비용으로 주되 중단 지점을 통제할 수 없고, async는 이론상 더 낮은 오버헤드로 동시성을 주되 중단 지점을 통제할 수 있다.

**멀티프로세싱.** CPU 바운드 작업에는 `multiprocessing` 모듈을 쓴다. 초기화되면 새 OS 프로세스들을 띄우는데, 각자 자기 자원과 **자기 파이썬 인터프리터**를 갖는다. 인터프리터를 얻는 방식은 시작 메서드마다 달라서, 이미 돌고 있는 인터프리터를 복제해 빠른 방식도 있고 파이썬 프로세스를 처음부터 새로 띄워 모듈을 재임포트하고 상태를 다시 만드는 방식도 있다. 결과적으로 N개의 인터프리터와 N개의 GIL이 서로를 모른 채 존재한다 — 멀티프로세싱은 GIL을 공유하지 않는 방식으로 GIL을 우회한다. 이제 OS가 각 프로세스를 자기 코어에 올려 바이트코드를 동시에 실행할 수 있다. 진짜 병렬성의 대가는 두 군데서 나온다. 첫째, 프로세스 시작이 스레드보다 무겁다. 둘째, 데이터 공유에 추가 노력이 든다 — 프로세스끼리 객체를 직접 건넬 수 없어 파이썬 기본값은 Queue나 Pipe를 통해 전부 pickle 하는 것이라 메시지마다 직렬화 비용을 낸다. 공유 메모리로 이를 피할 수 있지만 바이트나 수치 배열 같은 평평한 데이터에만 되고 임의의 파이썬 객체에는 안 된다.

**적용 각도(참고용 메모)**: 이 파이프라인의 LLM 호출부가 `make_async_client()` 기반 asyncio인데, `claude -p` 서브프로세스 폴백처럼 블로킹 가능성이 있는 경로가 단일 이벤트 루프를 세울 수 있다는 점(글의 "블로킹 호출 하나가 전체를 멈춘다")을 점검해볼 만하다.
