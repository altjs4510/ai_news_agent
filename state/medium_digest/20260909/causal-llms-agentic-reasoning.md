## 한글 요약

"하니스(harness)"가 에이전트 업계의 새 유행어가 됐다는 진단으로 시작한다. 기업에서 에이전트를 만드는 건 쉬워졌고, 어려운 건 일관되게 대규모로 운영하는 일이다. 그래서 초점이 LLM 자체에서 LLM 을 감싸는 하니스로 이동했다 — 고립된 지능에서 관리되는 실행으로. 저자가 꼽는 하니스 구성 요소는 추론 루프(계획 그래프 생성→실행→반성→적응), 컨텍스트·메모리 관리(단기 기억 요약 후 장기 기억으로 승격), 평가(LLM-as-a-Judge), 보안(사용자→앱→에이전트→도구→소스 시스템 사이 표준화된 상호작용), 가드레일(프롬프트 인젝션·도구 오용·메모리 오염), 그리고 인간을 감독자가 아닌 1급 참여자로 넣는 HITL 이다.

이 글은 그중 추론 루프에 집중한다. 지금 에이전트는 작업 분해를 LLM 에 맡기므로 LLM 의 추론 한계가 곧 에이전트의 한계다. 저자는 이커머스 예시(신용 확인, 배송 방식 선택처럼 실행될지 안 될지가 런타임에 갈리는 비결정적 연산자)를 들어, 계획에는 컴포넌트 에이전트 사이의 **인과 관계**를 이해하는 다단계 추론이 필요하다고 주장한다. 근본 문제는 "상관은 인과가 아니다" — 모델이 아무리 커도 학습 데이터의 통계적 상관만 잡을 뿐 인과 이해는 빠져 있다.

2절은 비즈니스 워크플로우의 에이전트화 절차다. 요구사항 수집→에이전트 계층·스킬·도구 설계→안전한 구현→거버넌스까지의 전 수명주기가 필요하며, 인간 개입 지점을 네 가지로 설계한다: **Co-plan**(생성된 오케스트레이션 그래프가 의도와 맞는지 검증), **Co-execute**(실행 중 일시 정지·피드백), **Co-comply**(결제 같은 되돌릴 수 없는 작업을 표시하고 정책 준수를 확인 후 승인), **Co-memorize**(장기 기억 개념을 검토·정리). 여기에 과거 상호작용에서 배워 미래 개입을 최적화하는 지속 개선 모듈이 붙는다.

Co-planning 의 구체 절차로 기존 SOP·프로세스 맵을 재료로 쓰는 방식을 제시한다. 문서를 인제스트하고, LLM 에게 단계를 뽑아 에이전트 함수에 매핑시키고, 각 단계에 원문 참조를 달아 환각을 줄이고, 논리 OR 로 묶인 복잡한 단계는 원자 단계로 쪼개고 중복은 병합하며, 단계마다 준수·위반 예시를 생성해 모호함을 없앤다. 도메인 전문가가 대화형 인터페이스로 초안을 고쳐 "나쁜 수동 프로세스의 자동화"를 막고, 검증된 프로세스는 마켓플레이스의 등록 에이전트·도구와 매칭해 재사용을 극대화한다.

3절은 인과 추론 도입 근거다. Apple 의 두 논문을 인용해 최신 LLM 이 같은 문제의 변형, 다중 절 문제, 관련 있어 보이는 무관 정보 앞에서 최대 65% 정확도 하락을 보였고, 대형 추론 모델(LRM)은 일정 복잡도를 넘으면 완전히 붕괴하며 토큰 예산이 충분해도 추론 노력이 오히려 줄어드는 역설적 스케일링을 보인다고 정리한다. 명시적 알고리즘을 줘도 소용없었다는 점에서, 모델은 논리적 추론이 아니라 학습 데이터에 있던 추론 단계를 흉내내는 것이라는 결론이다. Gartner 2024 하이프 사이클도 인과 AI 를 혁신 촉발 단계로 올렸다.

제안은 LLM 학습·파인튜닝 레시피에 **지식그래프 + 인과 AI 모델**을 재료로 넣는 것(WHAT·HOW·WHY 를 함께 공급). 인과 모델이 주는 요소는 근본 원인 순위화, what-if·반사실 시나리오, 왜 어떤 행동이 나은지의 설명, 교란 변수 식별, 결과에 이르는 경로 이해다. 신용 리스크 평가 예시처럼 특징 간 인과 방향·강도를 그래프로 모델링하고, 이를 마이크로서비스처럼 조합 가능한 인과 컴포넌트 모델로 쌓은 뒤 RL 이나 STaR 류 자기 학습 루프로 지속 개선한다. 도메인 특화 소형 언어 모델(SLM)을 "그라운드 트루스"로 두어 환각을 억제하는 방향도 언급한다.

4절은 학습이 아니라 추론 시점의 개선으로, 제조·산업 IoT 사례에서 ReAct 만으로는 도메인 추론 공백(냉각기 톤수와 에너지 효율 연결), 날짜 오프셋 추론 불일치, 조기 종료·중복 도구 호출·다단계 조합 실패가 나타났다고 한다. 해법은 **ReAct + 인트로스펙션**: 전처리 증류 모듈이 질의를 변수·제약·목표로 구조화하고, 오케스트레이터가 실행 전 엔티티 명확화를 위한 내부 서브쿼리를 먼저 던진다. 실행 후 LLM-as-a-Judge 리뷰 모듈이 결과를 달성/부분 달성/실패로 분류하고, 실패 시 반성 모듈이 실패 원인을 진단해 새 실행 계획을 세우며 그 피드백(계획 변경·추론 템플릿)을 시스템 프롬프트에 누적한다. 이전 시도의 질의·계획을 주고 실패 이유와 새 고수준 계획을 문장으로 쓰게 하는 프롬프트 골격도 소개된다.

결론적으로 LLM 의 추론 한계가 기업 에이전트 자율성의 병목이며, 인과성은 비즈니스 워크플로우에 본래 내재해 있으니 학습 단계엔 인과 모델·지식그래프를, 추론 단계엔 인트로스펙션을 넣자는 제안이다.

**적용 각도(참고용 메모)**: SOP→에이전트 단계 추출(원문 참조 부착·OR 분해·준수/위반 예시 생성) 절차는 사내 업무 지식을 OKF 번들이나 스킬로 옮길 때 그대로 체크리스트로 쓸 수 있고, 실패 진단→계획 수정 피드백을 시스템 프롬프트에 누적하는 인트로스펙션 루프는 하니스 워커의 재시도 설계와 맞닿는다.
