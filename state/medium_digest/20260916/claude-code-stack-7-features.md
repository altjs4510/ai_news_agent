## 한글 요약

필자의 출발 논지는 Claude Code 의 성격 자체가 바뀌었다는 것이다. 예전엔 터미널 안에 앉은 유능한 프로그래머에 가까웠다 — 일을 주면 파일을 뒤지고, 코드를 쓰고, 명령 몇 개를 돌려 결과를 돌려준다. 그 기능이 사라진 건 아니지만, 최근 추가된 기능들을 묶어 보면 제품이 겨냥하는 지점이 "코드를 잘 쓰는 모델"이 아니라 "AI 가 실제로 개발 업무를 수행할 수 있는 환경"임이 드러난다는 주장이다. 필자가 꼽은 구성 요소는 일곱 개 — CLAUDE.md, Skills, 서브에이전트, Hooks, MCP, 백그라운드 실행, 에이전트 팀.

**1) CLAUDE.md — 프로젝트 기억.** 코딩 에이전트의 가장 단순하면서도 큰 문제는 그 레포가 어떻게 굴러가는지를 자동으로는 모른다는 점이다. 코드는 읽을 수 있지만, 정해진 테스트 명령, 절대 건드리면 안 되는 파일, 팀의 네이밍 규칙, 지키길 바라는 아키텍처 같은 건 코드만 봐선 드러나지 않는다. 세션마다 같은 설명을 반복하는 대신 그 규칙들을 에이전트가 접근할 수 있는 자리에 적어 두는 것이 CLAUDE.md 다. 기능 자체는 기초적이지만, 필자는 이 "지속되는 컨텍스트"야말로 매번 브리핑해야 하는 챗봇을 개발 환경의 일원에 가깝게 만드는 요소라고 본다.

**2) Skills — 같은 절차를 다시 설명하지 않기.** 릴리스 노트 생성, PR 리뷰, 특정 테스트 워크플로, 문서 작성 시 따라야 할 절차처럼 반복되는 작업은 매번 설명하거나, 한 번 Skill 로 만들어 두거나 둘 중 하나다. 필자가 강조하는 구분은 이것이 "더 나은 프롬프트 쓰기"가 아니라 **필요해질 때 에이전트가 스스로 불러 쓰는 재사용 가능한 능력을 만드는 일**이라는 점이다. 정리하면 — 지시(CLAUDE.md)는 프로젝트가 어떻게 돌아가는지를, 스킬은 반복 업무를 어떻게 수행하는지를 알려준다.

**3) 서브에이전트 — 한 에이전트에 전부 떠넘기지 않기.** 큰 작업은 낯선 라이브러리 조사, 기존 코드 분석, 구현, 테스트 실행, 변경 리뷰처럼 성격이 다른 일들의 묶음이다. 서브에이전트는 이 조각들을 각자의 컨텍스트를 가진 전문 에이전트에 위임하게 해준다. 개발자 한 명을 작은 팀으로 바꾸는 셈이다. 핵심 이점은 "AI 를 더 많이 쓰는 것"이 아니라 **일을 분리하는 것** — 거대한 단일 컨텍스트 창에 모든 세부를 밀어 넣는 대신, 각 에이전트가 자기 문제에 집중하고 쓸모 있는 결과만 돌려주는 쪽이 훨씬 확장성 있는 구조라는 논지다.

**4) Hooks — 규칙은 코드가 강제한다.** 화려하진 않지만 필자가 개발자들에게 특히 주목하라고 하는 항목. "매번 이렇게 해 줘"라고 모델에게 부탁하는 것과, 코드로 자동 실행되게 만드는 것은 근본적으로 다르다. Hooks 는 Claude 가 특정 도구를 쓰기 전후에 동작을 끼워 넣게 해준다 — 특정 작업 차단, 검증 단계 실행, 로깅, 후속 프로세스 트리거, 결과 자동 확인 등. 이게 중요한 이유는 에이전트가 확률적이기 때문이다. 반드시 일어나야 하는 일을 모델 지시에만 맡겨선 안 된다. 여기서 필자가 현대 에이전트 아키텍처를 관통하는 원칙으로 뽑는 한 줄: **판단이 필요한 곳은 모델에게, 신뢰성이 필요한 곳은 코드에게.**

**5) MCP — 바깥 세계로의 접근.** 레포 안의 파일만 만질 수 있는 에이전트는 한계가 뚜렷하다. MCP 는 데이터베이스, API, 문서, 프로젝트 관리 시스템, 사내 도구 등 외부 서비스에 에이전트를 연결한다. 이로써 질문이 "Claude 가 어떤 코드를 쓸 수 있나"에서 "Claude 가 실제로 무엇에 접근할 수 있나"로 옮겨간다. 강력한 모델이라도 쓸 도구가 없으면 제한적이고, 적절한 시스템에 연결된 모델은 전혀 다른 종류의 작업자가 된다는 것.

**6) 백그라운드 실행 — 사람을 기다리지 않는 작업.** 전통적 AI 상호작용은 묻고-답하는 루프였다. 필자는 예약·자율 워크플로(cron 성격의 `/schedule` 실행 등)가 이 관계를 바꾼다고 본다. "지금 이거 해 줘"에서 "이걸 지켜보다가 해야 할 때 해 둬"로. 터미널 앞에 앉아 있어야만 일이 진행되는 게 아니게 되고, 도구·스킬·서브에이전트와 결합되면 함의가 커진다.

**7) 에이전트 팀 — 개발자 한 명이 팀이 된다.** 스택에서 가장 야심찬 부분. 복잡한 프로젝트 전체를 한 세션에 맡기는 대신 여러 에이전트가 각 부분을 맡는다 — 하나는 이슈를 조사하고, 하나는 코드를 고치고, 하나는 구현을 검증하는 식. 요점은 병렬 처리가 아니라 **위임**이다. 리드 개발자가 모든 작업을 직접 하지 않고 문제를 나누고, 책임을 배정하고, 결과를 리뷰해 합치는 그 조직 구조가 에이전트 쪽에도 생겨나고 있다는 비유다.

마무리에서 필자는 개별 기능 각각은 소프트웨어 개발을 뒤집을 만한 게 아니며 그게 요점도 아니라고 못 박는다. 의미는 연결에서 나온다 — CLAUDE.md 가 맥락을, 스킬이 재사용 워크플로를, 서브에이전트가 위임을, Hooks 가 결정론적 통제를, MCP 가 외부 시스템 접근을, 백그라운드 실행이 시간을, 에이전트 팀이 규모를 준다. 그러면 AI 에게 함수 하나를 써 달라고 부탁하는 게 아니라, 이해하고 판단하고 행동하고 위임하고 검증할 수 있는 환경을 쥐여 주는 것이 된다. 그래서 논의의 무게중심도 "Claude 에게 가장 좋은 프롬프트는 무엇인가"에서 "Claude 가 무엇에 접근할 수 있어야 하고, 무엇을 할 수 있어야 하며, 그 주위로 일이 어떻게 조직되어야 하는가"로 옮겨간다. 필자는 이것을 프롬프트 엔지니어링과 구분해 **에이전트 엔지니어링**이라 부르고, 코딩 어시스턴트는 사라지는 게 아니라 더 큰 시스템 안의 작업자가 되어 간다는 말로 끝맺는다.

**적용 각도(참고용 메모)**: "판단은 모델, 강제는 코드" 원칙은 이 파이프라인에도 그대로 닿는다 — 예컨대 x_trends 에서 예시 링크를 LLM 이 아니라 코드가 문자열 매칭으로 찾게 한 결정(URL 할루시네이션 방지)이 정확히 그 패턴이고, 이 무인 다이제스트 작업의 "제목 불일치면 저장하지 않는다" 가드도 같은 계열이다.
