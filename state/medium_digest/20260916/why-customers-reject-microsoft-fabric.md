## 한글 요약

Power BI 컨설턴트인 필자가 실제 고객사 한 곳의 의사결정 사례를 들어, Microsoft Fabric 도입이 왜 거부당하는지를 정리한 글이다. 톤은 상당히 날이 서 있고 본인도 이를 건설적 비판으로 받아들여 주길 바라지만 아마 아무도 듣지 않을 거라고 냉소하며 시작한다. 다만 전제는 공정하게 깔아 둔다 — Fabric 이 지난 1년간 많이 발전했고, 3년 만에 드디어 비즈니스 크리티컬하지 않은 워크로드라면 프로덕션에서 그럭저럭 쓸 만해졌다는 점은 인정한다. 이 글의 주장은 그럼에도 다수 고객이 채택하기까지는 갈 길이 멀다는 것이다.

고객사 배경은 이렇다. 필자가 10년 넘게 함께 일한 곳으로, 조직 내 Power BI 도입과 교육을 필자가 도왔고, 온프레미스 SQL Server 를 Azure SQL Server 로 옮기는 작업도 함께 했다. 그 서버는 수백 GB 규모의 데이터베이스를 5년간 문제없이 돌려 왔지만 데이터가 계속 늘면서 느려지기 시작했고, 할 수 있는 튜닝은 다 했으며 스케일업 여력도 거의 바닥났다. 그래서 더 잘 확장되는 다른 방안을 찾아야 하는 상황이었고, 이미 (원하지도 않은) Fabric SKU 로 떠밀려 있던 터라 Fabric 을 아주 진지하게 들여다봤다. FabCon 까지 다녀온 뒤 내린 결론은 "안 쓴다"였다는 것.

**첫 번째 문제 — CU 소모가 비상식적이다.** 이 고객은 F32 용량에서 10GB짜리 SQL 데이터베이스를 Fabric SQL Server 로 복원해 봤는데, 그 복원 시도만으로 거의 즉시 용량의 CU(capacity unit)가 고갈됐다. 필자는 "단순해 보이는 작업이 CU 를 너무 많이 먹는다"는 불평을 고객들에게서 자주 듣는다고 덧붙인다.

**두 번째 문제 — 비용을 미리 알 수 없다.** 첫 번째와 맞물린 지점으로, 어떤 작업이 CU 를 얼마나 쓸지 알 방법이 사실상 없다는 것. CU 라는 단위가 너무 추상화돼 있어서 특정 연산의 비용을 사전에 계산할 수 없고, 그래서 "이 단순한 작업을 하다 용량이 터질 것인가"에 아무도 답해 줄 수 없다. 고객사는 이 예측 불가능성 자체에 크게 불안해했다.

**세 번째 문제 — 예약 인스턴스를 업그레이드할 수 없다.** 앞의 둘이 치명적으로 결합되는 대목이다. F32 예약 인스턴스를 쓰다가 CU 가 모자라 F64 가 필요해져도 기존 예약분을 상향 조정할 수 없고, 완전히 새로운 Fabric 용량을 통째로 새로 사야 한다. 필자는 여기서 가장 강하게 분노하는데 — F64 와 F32 의 월 가격 차이에 예약 잔여 개월 수를 곱해 그 차액을 받으면 되는 단순 산수인데 그걸 안 해 준다는 것. 고객 서비스가 이토록 나쁜데도 사업이 유지된다는 게 놀랍다는 식의 논평을 붙인다.

**네 번째 문제 — 재해복구(DR)가 부실하다.** 고객사는 이 대목을 필자보다 정중하게 표현했다지만, 필자 표현으로는 Fabric 의 DR 은 농담 수준이다. 특히 Fabric SQL 데이터베이스는 지리적 복제(geo-replication)를 아예 지원하지 않는다. 레이크하우스·웨어하우스에는 geo-replication 이 있지만, Fabric 이 파일은 백업해 주되 웨어하우스/레이크하우스 자체는 백업하지 않는다는 점을 지적한다(본인도 다소 단순화한 설명이라고 단서를 단다). 결과적으로 사고가 나면 처음부터 수작업으로 전부 재구축해야 한다는 것이고, 이 불만 역시 고객들에게서 반복해서 듣는다고 적는다.

필자가 묶어 내는 결론은 락인 구조에 대한 것이다 — 요청한 적 없는 SKU 로 떠밀고, 예약 인스턴스는 업그레이드가 막혀 있어 CU 가 더 필요하면 새 용량을 사느라 돈을 버려야 하며, 그런 상태에서 회사의 생명줄인 데이터를 그 안에 넣으라고 요구하면서 정작 일이 터지면 복구는 알아서 수작업으로 하라는 그림이라는 것. 사례 하나에 기반한 강한 논조의 글이지만, 그가 반복해 듣는다고 말하는 세 가지 불만(불투명한 CU 과금, 상향 불가한 예약, 약한 DR)은 Fabric 도입을 검토할 때 실제로 확인해 볼 만한 구체적 체크포인트다.

**적용 각도(참고용 메모)**: "비용 단위가 추상화되어 사전 예측이 불가능하다"는 불만은 LLM 토큰 과금·회사 LiteLLM 쿼터에도 그대로 옮겨붙는 구조다 — 이 파이프라인이 구독(정액) 우선 + 프록시 폴백으로 간 결정이 정확히 그 예측 불가능성을 피하려는 선택이었다.
