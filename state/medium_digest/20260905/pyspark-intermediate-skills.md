## 한글 요약

시리즈 3편에 해당하는 글로, SparkSession 생성·DataFrame 적재·스키마 정의·조인·Parquet 쓰기까지 익힌 사람이 다음으로 부딪히는 질문들을 다룬다. 왜 갑자기 잡이 느려지는가, 왜 단순한 `groupBy()`가 예상보다 오래 걸리는가, 왜 출력 파일이 그렇게 많이 생기는가, 언제 캐시해야 하는가, 그리고 도대체 셔플이 뭔가. 클러스터 튜닝이나 YARN·쿠버네티스 같은 내부로 파고들지 않고 실무적 감각에 집중한다. 관통하는 주제는 하나다 — **중급 PySpark는 대부분 데이터 이동을 이해하는 일이다.**

처음 배울 때는 코드에 집중하지만, 이 단계에서는 각 줄이 뒤에서 무엇을 시키는지를 생각해야 한다. 행 필터링처럼 값싼 연산이 있는가 하면(각 행을 보고 예/아니오 판단 후 넘어가면 끝), `groupBy("customer_id").sum("amount")`처럼 같은 고객의 모든 행을 한곳에 모아야 하는 연산이 있다. 코드는 똑같이 한 줄이지만 비용은 데이터 이동에서 나온다. 그래서 튜닝 설정에 손대기 전에 던질 질문은 단순하다 — **이 줄이 스파크에게 데이터를 옮기라고 강요하는가?**

**파티션.** DataFrame은 하나의 덩어리가 아니라 병렬 처리 가능한 조각들로 나뉜다. `df.rdd.getNumPartitions()`로 확인할 수 있다. 파티션이 너무 적으면 가용 CPU 코어를 다 못 쓰고, 너무 많으면 자잘한 태스크 관리에 시간을 낭비한다. `repartition(16)`은 개수를 늘리거나 줄일 수 있지만 대개 데이터 재분배를 유발해 성능 비용이 따르고, `coalesce(4)`는 주로 줄이는 용도이며 데이터 이동이 적다. 실용적 규칙 — 데이터를 더 고르게 펴야 하면 `repartition()`, 그냥 출력 파일 수를 줄이고 싶으면 `coalesce()`. 예컨대 작은 Parquet 파일이 너무 많이 생기면 `df.coalesce(4).write...parquet(...)`로 네 개만 쓰게 한다. 이 단계에서 정확한 파티션 수에 집착할 필요는 없고, 파티션이 작업 분할을 통제한다는 점만 알면 된다.

**셔플.** 파티션 안에서 끝나는 연산이 있고, 서로 다른 파티션의 데이터를 한데 모아야 하는 연산이 있다. 후자가 셔플이다. 드물지도 않고 자동으로 잘못된 것도 아니지만 대개 비싸다. `groupBy()`, `join()`, `distinct()`, `orderBy()`, `repartition()`이 셔플을 일으킬 수 있는 대표 연산이다. 고객별 합계는 그 고객의 모든 행이 모이지 않으면 계산할 수 없고, 전역 정렬은 파티션 내부가 아니라 데이터셋 전체를 비교·배열해야 한다. 잡이 느리면 셔플부터 의심하라는 것이고, 좋은 습관은 **비싼 연산 앞에서 미리 걸러내는 것**이다. 조인한 뒤 런던 고객만 필터링하지 말고, 런던 고객만 먼저 필터링한 뒤 조인하라 — 옮길 데이터 자체가 줄어든다.

**조인.** PySpark 잡이 느려지는 지점의 상당수가 조인인데, 조인이 나빠서가 아니라 양쪽 데이터셋의 행을 매칭하려면 데이터를 옮겨야 하기 때문이다. 세 가지 실무 처방을 준다. 첫째, 조인 키의 데이터 타입을 맞춘다 — 한쪽이 정수 ID, 다른 쪽이 문자열 ID면 오류나 예상치 못한 결과가 나오므로 `F.col("customer_id").cast("string")`으로 명시적으로 캐스팅한다. 둘째, 조인 전에 필요한 컬럼만 `select()`하고 가능하면 행도 미리 필터링한다. 셋째, 작은 룩업 테이블은 **브로드캐스트**를 고려한다 — `from pyspark.sql.functions import broadcast` 후 `df_sales.join(broadcast(df_customers_small), ...)`. 한쪽이 충분히 작으면 양쪽을 셔플하는 대신 작은 쪽을 각 워커에 복사하는 방식이고, 고객 정보·국가 코드·상품 카테고리·환율 같은 룩업에 특히 유용하다. 다만 남용하지 말라고 경고한다 — 큰 테이블을 브로드캐스트하면 메모리 문제가 생긴다.

**실행 계획 읽기.** PySpark는 지연 평가라 변환을 즉시 실행하지 않고 계획을 쌓는다. `df.explain("formatted")`로 그 계획을 볼 수 있는데 처음엔 서류함을 화면에 쏟아부은 것처럼 보인다. 전부 이해할 필요는 없고 몇 개 단서만 알아보면 된다 — `Scan`은 데이터 읽기, `Filter`는 필터 적용, `Project`는 컬럼 선택이나 파생 컬럼 생성, `SortMergeJoin`은 키를 정렬해 매칭하는 조인, `HashAggregate`는 그룹화 후 집계, `BroadcastHashJoin`은 브로드캐스트 조인. 가장 먼저 봐야 할 것은 **`Exchange`** — 파티션 간 데이터 이동, 즉 셔플이 일어난다는 뜻이다. 자동으로 나쁜 건 아니지만 비용이 어디에 있는지 알려준다. 로컬 실행 중이면 `http://localhost:4040`의 Spark UI로 어떤 스테이지가 오래 걸리는지도 볼 수 있다. 내부 전문가가 될 필요는 없고 가끔 열어보는 습관이면 충분하다.

**캐싱.** "빠르게 만들기" 마법 버튼처럼 느껴지지만 때론 메모리만 잡아먹는다. `df.cache()`는 지연 평가이므로 그 자체로는 아무것도 캐시하지 않고, "계산되면 메모리에 두라"고 표시할 뿐이다. `count()` 같은 액션이 있어야 실제로 물질화된다. 캐싱은 **같은 세션에서 같은 DataFrame을 여러 번 재사용할 때만** 유용하다 — 정제된 데이터셋을 도시별 집계, 등급별 집계, 필터링에 연달아 쓰는 경우라면 도움이 되지만, 한 번만 쓰고 마는 DataFrame을 캐시하면 오버헤드만 추가된다. 해제는 `unpersist()`. 규칙 — 생성 비용이 크고 두 번 이상 재사용하는 것만 캐시하라, 전부 캐시하지 마라, PySpark 메모리는 귀하다.

**파티셔닝된 쓰기.** `.partitionBy("year", "month")`로 Parquet을 쓰면 `year=2026/month=1/` 같은 폴더 구조가 생기고, 나중에 `filter(F.col("year") == 2026)`으로 읽을 때 스파크가 2025 폴더를 아예 읽지 않을 수 있다. 이것이 **파티션 프루닝**이고 필터가 파티션 컬럼과 맞을 때 읽기가 크게 빨라진다. 좋은 파티션 컬럼은 자주 필터링하는 필드(연·월·지역·국가·부서)다. 단 고유값이 너무 많은 컬럼은 금물 — `partitionBy("transaction_id")`처럼 하면 수천~수백만 개의 미세 폴더와 파일이 생겨 관리도 읽기도 나빠진다. 날짜 기반 파티셔닝이 무난한 출발점이다.

**UDF보다 내장 함수.** 파이썬 UDF는 유용한 경우가 있지만 내장 함수보다 느릴 수 있다. `F.upper("customer_name")`은 스파크가 이해하고 실행 계획의 일부로 최적화하지만, 같은 일을 하는 파이썬 UDF는 최적화 여지가 적고 스파크 엔진과 파이썬 사이를 데이터가 오가는 오버헤드가 붙는다. 내장 SQL 함수를 먼저 쓰고, 대응하는 함수가 없을 때만 UDF로 가라는 것이다.

**데이터가 커질 때의 함정들.** `collect()`는 모든 데이터를 드라이버의 파이썬 메모리로 가져오므로 큰 데이터에서는 드라이버를 압도한다 — 살펴보려면 `show()`, 결과가 필요하면 파일로 쓰라. `count()`는 액션이라 데이터를 스캔하므로 생각 없이 곳곳에 뿌리지 말 것. 전역 정렬은 셔플을 부르니 상위 몇 건만 필요하면 `orderBy(F.col("amount").desc()).limit(10)`로 top-k 최적화를 유도하라. 조인 후 필터링 대신 조인 전 축소, 작은 파일 남발은 `coalesce()`로 정리. 그리고 가장 강조하는 것 — 파이썬 루프로 도시마다 `filter().count()`를 돌리면 별개의 잡이 여러 개 생기니 `groupBy("city").count()` 한 줄로 대체하라. 스파크는 원하는 **결과를 서술하고 경로 계획은 맡길 때** 가장 행복하다.

마지막에는 이 조각들을 하나의 워크플로로 조립해 보여준다: 파티셔닝된 Parquet에서 최근 매출을 읽고 → 필요한 컬럼만 select 하고 → 결측 제거와 조인 키 캐스팅으로 정제하고 → 작은 고객 룩업을 broadcast 조인하고 → 축소된 데이터로 집계하고 → 연·월로 파티셔닝해 쓰고 → `explain("formatted")`으로 계획을 확인하는 순서다. 예상되는 물리 계획에는 `BroadcastHashJoin`(브로드캐스트 힌트가 반영됐다는 좋은 신호)과 `groupBy` 때문에 예상된 `Exchange`가 나타나고, 매출 데이터가 연도로 파티셔닝돼 있다면 파일 프루닝도 볼 수 있다.

요약하면 중급 PySpark는 설정값 암기가 아니라 소수의 아이디어를 이해하는 일이다 — 데이터는 파티션으로 나뉘고, 어떤 연산은 독립적으로 돌고 어떤 연산은 셔플을 요구하며, 조인은 강력하지만 비싸고, 캐싱은 재사용할 때만 도움이 되고, Parquet 레이아웃이 읽기 성능을 좌우하고, 내장 함수가 대개 UDF보다 빠르고, 실행 계획이 무슨 일이 벌어지는지 보여준다. 이것들이 잡히면 느린 잡이 더 이상 무작위로 느껴지지 않고 원인이 보이기 시작한다 — 여기 셔플 하나, 저기 넓은 조인 하나, 어딘가의 자잘한 파일 더미.

**적용 각도(참고용 메모)**: "비싼 연산 앞에서 먼저 줄여라"와 "고유값 많은 컬럼으로 파티셔닝하지 마라"는 스파크 밖에서도 유효한 원칙이다 — 우리 파이프라인의 날짜 기반 `state/`·`reports/` 디렉토리 구조가 정확히 후자의 안전한 형태이고, LLM 호출 전에 소스를 걸러 토큰을 줄이는 것이 전자의 대응물이다.
