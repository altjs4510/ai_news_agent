## 한글 요약

"AI가 곧 개발자를 필요 없게 만든다"는 통념에 반박하는 글 — 모든 프로그래밍 언어가 "같은 것의 다른 문법"이 아니라, 언어마다 코드 한 줄 뒤에 숨은 "중첩된 의미론적 맥락"의 깊이가 다르다는 게 핵심 주장.

**C++ 사례**: AI가 템플릿·RAII·이터레이터·람다 등 겉보기엔 그럴싸한 C++ 코드를 잘 생성하지만, 그게 "신뢰할 수 있는 프로젝트를 만든다"는 뜻은 아니라는 것. 이름 조회(name lookup), ADL, 템플릿 의존성, 오버로드 해석, concept, 값 카테고리, 객체 수명, 소유권, 동시성처럼 코드 한 줄 자체엔 안 보이는 여러 층의 의미론이 동시에 맞아야 정확한데, 이게 `code → meaning`이 아니라 `(code, nested contexts) → meaning`에 가깝다는 게 문제. 같은 `process(x)`라는 표현도 어떤 "의미론적 우주"(타입·룩업 규칙·ADL 경로가 다른 맥락)에 있느냐에 따라 완전히 다른 의미가 됨 — AI는 이 우주 전환을 놓치기 쉬움.

**Haskell 사례**: `runST` 안에서 만든 가변 참조를 밖으로 반환하려는 코드 — 각 줄은 로컬로 보면 다 정상이지만, 그 참조가 `runST`가 만든 private한 타입 레벨 컨텍스트(`s`)에 묶여 있어서 전체 프로그램이 illegal. JS 클로저와 반대되는 개념(정보는 갖고 나올 수 있어도 그 정보를 만든 private mutable state 자체는 못 갖고 나옴)이라 AI가 자주 틀림.

**Rust 사례**: 소유권·차용(borrowing)·수명(lifetime) 문제. `let first = &v[0]; v.push(42); first`처럼 각 줄은 로컬로 유효해 보이지만, `first`가 `v`를 가리키는 상태에서 `v`를 변경하면 참조가 무효화될 수 있어 컴파일 에러 — 문제는 개별 줄이 아니라 줄 사이의 "관계"에 있음.

**근본 원인(저자 주장)**: 오늘날 LLM은 다음 토큰 예측 기반이라, 한 의미론적 맥락을 다른 맥락과 분리해서 지키는 규칙을 형식적으로 강제하지 못함 — 예시로부터 규칙을 배워 따라할 수는 있어도 모든 조합에서 정확함을 보장하진 못한다는 것.

**"AI가 잘 맞는" 언어들**: Python, JavaScript, Go, Lua, Java — 코드에 보이는 것과 실제 의미 사이 거리가 짧고(`visible code → local context → meaning`), 숨은 의미론적 레이어가 적음. 물론 이 언어들도 메타클래스·프로토타입·비동기 상태처럼 지저분해질 수 있지만, 대체로 맥락이 얕고 상호작용이 덜 격렬함.

**결론**: 코드가 눈에 보이는 그대로 의미가 결정되는 작업(보일러플레이트, 테스트 생성, API 번역 등)은 AI에 믿고 맡길 수 있지만, 소유권·수명·룩업·제약처럼 숨은 의미 구조에 정확성이 달린 프로젝트는 여전히 사람이 "어떤 맥락이 중요하고 뭘 깨면 안 되는지" 알아야 한다는 것.

**적용 각도(참고용 메모)**: 우리 파이프라인은 대부분 Python(AI에 우호적인 언어군)이라 이 리스크가 상대적으로 낮다는 정도로만 참고.
