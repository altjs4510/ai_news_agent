## 한글 요약

필자는 Claude Code 생태계 안에서 서로 통신하는 에이전트 팀을 실제로 구축해 본 뒤, 많은 사람들이 트레이드오프를 이해하지 못한 채 멀티에이전트로 뛰어들고 있다고 경고한다. 핵심 주장은 반직관적이다 — 서브에이전트가 잘 돌아간다고 해서 에이전트 팀이 "다음 단계"인 것은 아니다. 에이전트 팀은 실질적인 토큰 비용과 알려진 실패 양상을 가진 *조정 계층*이며, 잘 푸는 문제의 범위가 좁다.

필자가 강조하는 구분은 **역량(capability) vs 아키텍처**다. 에이전트를 추가한다고 시스템이 더 유능해지는 게 아니라 더 *분산*될 뿐이고, 분산은 업그레이드가 아니라 비용이다. LLM은 확률적이므로 에이전트를 하나 더 붙일 때마다 실패·환각·오해의 확률을 곱해 쌓는 셈이 된다. Anthropic의 "가장 단순한 해법에서 시작하고 필요할 때만 복잡도를 올려라"는 가이드를 그대로 인용한다.

단일 에이전트의 한계선은 **4가지 조건** 중 하나가 참일 때만 도달한다고 정리한다. ① 컨텍스트 격리 — 서브에이전트에 위임해도 작업이 컨텍스트 윈도우를 넘칠 때(가장 흔한 정당한 트리거), ② 특화 — 단순히 프롬프트가 다른 게 아니라 도구 접근 권한과 행동 제약 자체가 달라야 할 때(파일을 못 쓰는 코드 리뷰어 vs 코드 생성기는 리스크 프로파일이 범주적으로 다름), ③ 병렬성 — 상태를 공유하지 않는 독립 하위작업으로 쪼개지고 벽시계 시간이 중요할 때, ④ 독립 비평 — 첫 번째 추론에 오염되지 않은 제2 의견이 품질에 필요할 때. 어느 것도 지목할 수 없다면 단일 에이전트 경로가 여전히 옳다.

에이전트 조합 패턴은 4가지로 분류한다(필자가 Anthropic 문서에서 합성한 것이지 공식 분류는 아니라고 명시). **순차 파이프라인** — 단계 간 계약이 명시적이라는 게 강점이나 실수가 캐스케이드되므로 단계 사이 검증 게이트(JSON 계약 스키마 등)가 필수. **중앙 오케스트레이터/플래너-실행자** — 리드가 분해·위임·종합하고 워커끼리는 조정하지 않는 가장 유용한 기본값이며, Anthropic Research 기능이 정확히 이 패턴. 다만 위임 프롬프트가 모호하면 워커들이 검색을 중복하거나 경계를 놓치므로 각 워커에 목표·기대 출력 형식·소스 가이드·작업 경계를 명시해야 한다. **병렬 전문가/디베이트/레드팀** — 견고함이 중요할 때 쓰되 토큰 급증과 합의로 인한 거짓 확신 위험이 있다. **스웜/분산 공유컨텍스트** — 여기서부터 분산 시스템의 복잡도(소유권 모호, 공유 상태 경쟁, 디버깅 난이도)가 붙는다. 실무자 대부분은 앞의 두 패턴으로 충분하다고 본다.

Anthropic 스택은 원시 제어부터 호스팅 관리까지의 사다리로 정리한다: Messages API(루프를 직접 소유, 멀티에이전트 지원 없음) → Claude Agent SDK(에이전트 루프·컨텍스트 관리·서브에이전트·훅을 제공하고 Bedrock/Vertex/Azure Foundry 인증이 되어 이식성이 가장 좋음) → Claude Managed Agents(런타임 호스팅, 단일 에이전트는 성숙했으나 멀티에이전트 세션은 게이트된 별도 프리뷰) → Managed Agents multiagent(리서치 프리뷰, **코디네이터 계층이 1단계만** 지원 — 호출된 에이전트가 다시 다른 에이전트를 부를 수 없음) → Claude Code 서브에이전트(공식 기능) → Claude Code 에이전트 팀(2026년 4월 기준 **실험적·기본 비활성**, 환경변수로 켜야 하며 세션 재개 시 더 이상 존재하지 않는 팀메이트를 참조하는 등의 엣지케이스 존재). 요약하면 "Claude가 에이전트 팀을 지원한다"는 참이지만 "모든 표면에서 프로덕션급 범용 네이티브 멀티에이전트 오케스트레이션을 갖췄다"는 정확하지 않다.

서브에이전트와 에이전트 팀의 실질적 차이도 짚는다. 서브에이전트는 단일 메인 세션 안에서 격리 컨텍스트로 일하고 결과만 반환하며 오케스트레이션은 사용자가 한다. 에이전트 팀은 각자의 컨텍스트·세션 상태를 가진 별개의 Claude Code 세션들이 공유 작업 목록과 메일박스로 직접 통신하며, 리드를 거치지 않고 서로에게 작업을 할당하고 자율 조정한다. 설정은 `~/.claude/teams/{name}/config.json`(팀 구성)과 `~/.claude/tasks/{name}/`(공유 작업 목록)에 살고, 팀메이트 정의는 재사용 가능한 에이전트 파일이며 훅을 작업 전이 사이 품질 게이트로 쓸 수 있다. 문서가 명시적으로 밝히는 **에이전트 팀이 서브에이전트보다 나쁜 경우**는 순차 작업, 같은 파일 편집, 단계 간 의존성이 많은 작업이다.

에이전트 간 통신은 프롬프팅 문제가 아니라 시스템 문제라고 본다. 형식은 3가지 — 평문 메시지(가장 유연하지만 대규모에선 가장 신뢰성 낮음), 구조화된 호출(JSON Schema 도구 정의와 strict tool use로 스키마 준수를 보장), **공유 상태/아티팩트**(가장 과소평가된 형태). 특히 Anthropic의 멀티에이전트 리서치 시스템은 서브에이전트가 결과를 파일시스템이나 외부 시스템에 쓰고 가벼운 참조만 반환할 것을 권장하는데, 파일은 감사 가능하고 버전 관리되며 직접 검사할 수 있는 반면 파일을 요약한 메시지는 그중 아무것도 아니기 때문이다.

통신의 *타이밍*도 4가지로 나눈다: 동기 호출(추론은 쉽지만 느린 워커가 병목이 되고 중간 조향이 불가), 순차 핸드오프(소유권이 이전 — OpenAI는 핸드오프와 agents-as-tools를 구분하는데 이 구분이 책임 소재상 중요), 이벤트 기반/스트리밍(장기 작업에 유리하나 디버깅·테스트가 어려움), 공유 상태 폴링(가장 볼품없지만 종종 가장 견고 — Anthropic의 장기 실행 하네스가 JSON 피처 목록·진행 파일·git 커밋을 지속적 공유 상태로 사용). 무엇을 넘기느냐도 중요한데, 전체 대화 이력은 연속성이 최대지만 비용·지연이 선형 증가하고, 압축 요약이 대체로 낫지만(서브에이전트의 기본 설계), 실질적 최적점은 **작업별 아티팩트**(구조화된 출력 파일, 코드 패치, JSON 피처 목록)를 넘기는 것이다 — 수신 에이전트가 요약을 신뢰하는 대신 아티팩트를 직접 검사할 수 있어 감사 가능성이 생긴다.

대부분의 튜토리얼이 건너뛰는 **8가지 실패 모드**가 이 글의 핵심이다. ① 조정 드리프트 — 모호한 위임으로 워커들이 검색을 중복하고 경계를 놓침(소유권을 정의하지 않으면 에이전트가 알아서 정하는데 형편없이 정한다). ② 환각된 소유권 — 한 에이전트가 다른 에이전트가 확인했겠거니 가정하지만 아무도 안 함. 해법은 명시적 완료 아티팩트와 종단간 검증. ③ 조용한 중간 실패 — 최상위 세션 스트림은 압축된 뷰일 뿐이라 워커 수준 이력을 봐야 실제로 뭘 했는지 알 수 있음. 첫 프로덕션 사고 이후가 아니라 처음부터 트레이싱을 계측하라. ④ 컨텍스트 팽창과 메모리 오염 — 모든 도구 호출·파일 읽기·부분 분석이 컨텍스트에 쌓여 남고 팀 전체에 걸쳐 복리로 증가. 완료 단계 요약, 무거운 작업 격리, 크고 공유된 메모리보다 작고 집중된 메모리 파일 선호가 완화책. ⑤ 스키마 불일치와 취약한 프롬프트 계약 — 자연어로 데이터를 주고받으면 두 번째 에이전트가 요약을 오해하고 오류가 조용히 전파. ⑥ 도구 오용과 보안 실패 — 열린 환경일수록 프롬프트 인젝션 진입점이 늘고, Anthropic은 이를 엣지케이스가 아니라 명명된 사이버공격 벡터로 규정하며, METR의 레드팀이 잘 갖춰진 내부 시스템에서도 신규 취약점을 발견함. 권한 제한, 작업에 필요한 만큼만 도구 노출, 중대한 행동에 대한 인간 승인 지점 보존이 완화책. ⑦ 비용 폭발과 지연 누적 — 병렬화는 벽시계 시간을 줄이지만 총 토큰 지출은 오히려 늘린다. ⑧ 평가 난이도 — 서로 다른 내부 궤적이 똑같이 그럴듯한 최종 출력으로 끝날 수 있어서, 최종 산문이 그럴듯한지만 본다면 시스템을 평가하는 게 아니라 감상하는 것이다. Anthropic의 권고는 의도한 *과정*을 따랐는지가 아니라 올바른 *최종 상태*에 도달했는지를 평가하라는 것.

마지막으로 직접 구축 vs 네이티브 선택은 3가지 트레이드오프로 정리한다. **네이티브 매니지드**는 엔지니어링 부담이 낮지만 이식성이 제약되고(Managed Agents는 직접 Claude API로만) 멀티에이전트 표면이 실험적이거나 게이트된 프리뷰 — 인프라가 고통일 때 적합. **DIY**(Messages API)는 제어가 최대·엔지니어링 비용도 최대 — 비즈니스 로직이 특이하거나 컴플라이언스가 엄격하거나 진짜 이식성이 필요할 때. **하이브리드**(Agent SDK)는 Anthropic이 루프와 도구를 주되 상위 설계는 직접 — 멀티에이전트에 대한 Anthropic의 현재 견해에 아키텍처 전체를 결혼시키지 않으면서 프리미티브는 쓰고 싶을 때. 결론은 4가지 트리거 중 어느 것이 실제로 참인지 먼저 이름 붙이라는 것이고, 하나도 없다면 단일 에이전트 경로가 여전히 정답이다.

**적용 각도(참고용 메모)**: ai_news_agent 는 현재 단일 파이프라인 + 소스별 수집기 구조라 4가지 트리거 중 어느 것도 명확히 참이 아니다 — 멀티에이전트화 유혹을 보류할 근거로 쓸 만하다. 다만 "작업별 아티팩트를 넘기고 수신 측이 직접 검사"라는 원칙은 이미 x_trends 가 LLM 대신 코드로 원본 posts 에서 링크를 매칭하는 설계(URL 할루시네이션 방지)와 같은 사상이라 교차 검증된다.
