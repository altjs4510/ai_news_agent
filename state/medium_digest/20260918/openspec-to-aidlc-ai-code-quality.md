## 한글 요약

필자(Mr. Qian)의 팀은 반년 넘게 AI로 코드를 써 왔는데 개발 속도는 올랐지만 코드 품질은 거칠게 남았다. 개발은 반나절이면 끝나는데 버그 추적에는 며칠이 걸리는 상황이었다. 그래서 한 달 넘게 팀의 AI 코딩 워크플로를 재구성하면서 OpenSpec을 AWS의 AIDLC 워크플로로 교체했고, 더 세밀한 개발 프로세스와 강한 팀 협업을 넣자 품질이 크게 올랐다는 경험담이다.

필자는 6개월 전만 해도 SDD(Spec Driven Development)가 최선의 답이라고 봤다고 말한다. SpecKit·OpenSpec 같은 규칙 프레임워크로 문답식으로 요구사항과 구현 규칙을 확정하고, 그 스펙 파일을 프롬프트로 넘겨 LLM이 엄격히 따르게 하는 방식이다. 그런데 이걸 **팀 전체에 롤아웃하고 나서** 깨달았다 — SDD는 작은 프로젝트에선 꽤 잘 돌아가지만, 프로젝트가 커지고 수년에 걸치며 여러 팀의 협업이 필요해지면 버티지 못한다.

OpenSpec이 무너진 지점을 6가지로 짚는다.

**① 사용법이 너무 복잡해졌다.** GitHub 문서의 명령어 중 몇 개나 기억하는가? `explore`와 `propose`를 정확히 언제 쓰는지 아는가? 필자는 각 명령을 언제 쓸지 설명하는 문서까지 따로 써서 배포했지만 여전히 어긋났다. explore가 propose 앞인가 뒤인가, 왜 곧장 plan 에이전트로 못 가는가 — 결국 팀원마다 제각각 쓰게 됐고, 일부는 시작할 때만 형식적으로 쓰고 이후엔 순수 바이브 코딩으로 돌아섰다. 추가 학습 비용이 개발자에게 값을 하지 못한 것이다.

**② 원래 의도를 전혀 붙잡지 못했다.** OpenSpec이 쓰는 스펙 파일은 사용자의 원래 의도나 원 요구사항을 저장하지 않고, plan 단계에서 사용자가 AI와 나눈 대화도 남기지 않는다. 그래서 다른 팀원이 쓴 스펙 파일을 리뷰할 때 길을 잃곤 했다 — 이 유저 스토리는 왜 이렇게 쓰였나, 이 메서드 설계는 대체 무슨 문제를 풀려던 건가. 시간이 지나면 코드를 쓴 개발자조차 왜 그렇게 설계했는지 잊는다. 원래 의도를 잃으면 프로젝트는 반복할 때마다 원래 목표에서 점점 멀어진다.

**③ 요구사항의 적절한 상세도를 잡기 어렵다.** explore/brainstorm 모드는 강력해서 오히려 "소원 기반 코딩(wish-based coding)" 함정으로 끌고 간다 — 한 문장이면 충분하고 AI가 알아서 단계별로 쪼개 완성품을 만들어 주리라 기대하게 되는 것. 하지만 현세대 LLM은 지름길 찾기에 매우 능해서, 모호한 목표를 주면 결국 주요 기능만 있는 데모가 나오고 세부 구현은 다 빠진 채 프로덕션에 못 올리는 반제품이 된다. 그래서 숙련 개발자는 기능을 잘게 쪼개 라운드별로 반복시킨다(1라운드 프로젝트 골격과 기술 스택, 2라운드 로그인·인증…). 그런데 이 분할 입도를 조절하는 게 정말 어렵다 — 너무 굵으면 데모가 되고, 너무 잘면 개발 속도가 떨어지며, 애초에 개발자가 생각 못 한 기능은 쉽게 누락된다.

**④ 문서가 현실과 어긋난다.** 팀원이 OpenSpec으로 스펙 문서를 쓴 뒤 코딩하면서 구현을 조정하는데, 명시적으로 OpenSpec 명령을 다시 부르지 않으므로 이후 조정분은 어떤 문서에도 반영되지 않는다. `tasks.md`의 문제를 발견해 고쳐도 따로 시키지 않으면 AI가 `design.md`를 알아서 건드리지 않는 상황도 있다. 반복이 쌓이면 이런 불일치가 도처에 생기고, 결국 스펙 파일은 참조 가치를 완전히 잃고 지저분한 코드 더미만 남는다.

**⑤ 언제 프로세스를 시작해야 할지 모른다.** 명령어와 개발 단계의 대응이 복잡해서 착수 시점을 진심으로 모르겠다는 팀원의 답변이 나왔다. `apply`로 코드를 막 끝냈는데 버그를 발견하면 AI에게 바로 고치라 할까 아니면 proposed 아티팩트 플로를 먼저 돌릴까? 버그를 고치는 중에 기존 기능을 손볼 아이디어가 떠오르면? 판단 기준이 없다.

**⑥ 팀 협업이 무너진다.** OpenSpec 같은 오픈소스 프레임워크는 하나같이 "AI의 도움으로 각자가 처음부터 끝까지 혼자 처리하는 슈퍼 개발자가 된다"고 가정한다. 하지만 실제 팀은 역할이 명확히 나뉘어 있고, 현대 비즈니스는 한 사람이 다 감당할 만큼 단순하지 않다. 요구사항 분석 문서와 유저 스토리를 썼으면 최소한 지표 계산 방식은 프로덕트 팀과 맞춰야 하고, 아키텍처 설계와 코딩 계획은 다른 개발자나 아키텍트가 봐야 한다. 그런데 OpenSpec은 propose로 스펙을 쓰기 시작해 코딩을 마칠 때까지 전 과정이 내 환경 안에서만 일어나며, 품질 게이트나 리뷰 메커니즘을 끼워 넣기도 매우 어렵다.

해법을 찾을 때 필자는 처음엔 AI로 새 워크플로를 직접 만들려 했지만, 수많은 팀에서 검증되지 않은 새 프로세스는 또 하나의 AI 장난감이 될 뿐 엔터프라이즈에 필요한 신뢰성이 없다고 판단해 접었다. 대신 6개월 전 뉴스를 떠올렸다 — 아마존 AWS가 주니어·미드레벨 엔지니어가 쓴 코드는 팀의 다른 사람이 리뷰·승인하도록 요구한 건이다. 아마존도 불안정한 AI 개발 프로세스가 프로덕션 사고를 낸 같은 문제를 겪었고 그때의 대응은 임시방편이었을 테니 지금쯤 체계적 해법이 나왔으리라 보고 찾아낸 것이 **aidlc-workflows**다. (필자는 2.0이 나왔지만 가볍고 확장하기 쉬운 1.0 기반에 커스터마이즈를 얹어 쓴다고 밝힌다.)

AIDLC는 AI Driven Development Life Cycle의 약자로 전통적 SDLC에 대응하는 개발 프로세스다. SDLC의 7단계(기획·요구사항 분석·설계·개발·테스트·배포·유지보수) 위에 **동적 워크플로**와 **동적 팀 협업** 두 능력을 더하고, 7단계를 3개 대분류로 묶는다. Inception 단계는 워크스페이스 탐지·조건부 하위단계·워크플로 계획을 맡아 "무엇을·왜"에 답하고, Construction 단계는 설계·구현·빌드·테스트를 맡아 "어떻게"에 답한다. 하위 단계가 많아 보이지만 항상 실행되는 것과 조건 충족 시에만 실행되는 것이 구분돼 있다.

**동적 워크플로 계획**은 "먼저 대화하고, 문서 쓰고, 구현한다"는 기존 SDD와 다르게 작동한다. 현재 프로젝트 환경과 대화 중 사용자의 선택에 따라 조건 분기하며 분기마다 다른 서브워크플로를 로드한다 — 복잡한 프로젝트는 더 많은 하위단계를, 작은 프로젝트는 더 단순한 것을. 예컨대 최초 로드 시 신규(Green Field)인지 기존(Brown Field)인지 확인해 기존이면 리버스 엔지니어링 워크플로로 기존 코드를 분석하고 신규면 통째로 건너뛴다. 새 요구사항이 제품의 최종 사용자에게 영향을 주는지 확인해 그럴 때만 user-stories 워크플로를 로드하고, 비기능 요구사항이거나 순수 프론트엔드 작업이면 건너뛴다. 또 `aidlc-state.md` 파일이 현재 단계를 추적하는 동시에, 소원 기반 개발을 하고 싶을 때 한 문장 요구사항을 분해해 가장 시급한 하위 요구사항부터 워크플로를 돌리고 나머지는 이 파일에 기록해 다음 라운드를 기다리게 한다 — **③의 요구사항 입도 문제를 이렇게 푼다**. 필자의 비유로는 핵심 워크플로가 대화에 늘 머무는 집사 같아서, 사용자의 말이나 프로젝트 상태가 조건을 트리거하면 캐비닛에서 맞는 서브워크플로 문서를 꺼내 넘긴다. 그래서 어떤 명령을 언제 쓸지 외울 필요도, 언제 프로세스를 시작할지 고민할 필요도 없다(**①·⑤ 해소**).

**동적 팀 협업**은 요구사항 분석 로깅과 승인 게이트 두 축이다. 대화 이력을 주로 컨텍스트에 남기는 기존 문답과 달리, AIDLC는 서브워크플로가 요구하는 시점마다 개발자에게 질문하고 모든 질문과 선택을 `{current-phase}-questions.md`에 기록한다. 각 하위 단계 끝에서 출력물을 손보거나 새 생각을 보태면 그 수정과 AI의 응답이 `audit.md`에 정리되어 저장된다 — **②의 원래 의도 미기록 문제를 이렇게 푼다**. 그리고 각 하위 단계 끝에서 워크플로가 **멈추고 사람의 리뷰를 기다린다**. 혼자 일하면 문서를 확인하고 "continue"라고 답하면 되고, 팀이라면 git으로 커밋해 동료에게 리뷰를 보낸다. 동료의 리뷰 노트와 표시가 audit.md에 기록되어 돌아오고, 내 AIDLC 인스턴스는 현재 단계의 승인 표시를 봐야만 다음 단계로 넘어간다. audit.md는 증분 업데이트만 지원하고 편집되지 않으므로 모든 변경과 리뷰 기록이 보존된다. extensions 폴더로 어떤 핵심 단계에 어떤 역할의 리뷰가 필요한지 설정할 수도 있다.

후반부는 필자가 팀 필요에 맞춰 만든 로컬 커스터마이즈를 다룬다. 우선 **AIDLC를 Skill로 전환**했다. AIDLC의 핵심은 `aws-aidlc-rules`(핵심 워크플로 정의)와 `aws-aidlc-rule-details`(온디맨드 로드되는 서브워크플로) 두 폴더인데, 기본적으로 아마존의 Kiro 에이전트를 지원하고 다른 에이전트용 공식 설정 절차는 아무도 끝까지 읽지 않을 만큼 복잡하다. 그런데 본질이 십여 개 마크다운 파일이므로 통째로 Skill로 만들 수 있다 — `.agents/skills` 아래 `aidlc-workflows` 폴더를 만들고 `core-workflow.md`를 `SKILL.md`로 복사·개명한 뒤, Agent Skills 스펙에 따라 rule-details의 모든 파일을 `references` 폴더로 복사하고 경로만 에이전트에게 정리시키면 끝이다.

확장 워크플로는 핵심 파일 `{workflow-name}.md`와 도입부 `{workflow-name}.opt-in.md`로 나뉜다. opt-in 파일은 요구사항 분석 단계에 로드되어 사용자에게 명확화 질문을 던지고, 그 답이 확장 워크플로가 어느 단계에 적용될지를 결정한다. opt-in 파일 없이 본 파일만 있으면 항상 로드된다. 이 구조 덕에 여러 확장을 동적으로 로드하면서 컨텍스트를 터뜨리지 않고 무한히 유지할 수 있다.

필자가 만든 확장은 네 가지다. **문서 일관성 유지** — 코드 변경이 생길 때마다 관련 워크플로 문서를 모두 갱신하게 해 ④의 스펙-코드 괴리를 막는다. **승인과 실행의 분리** — 기본 AIDLC는 승인하면 자동으로 다음 단계가 굴러가는데, 프로덕트 매니저가 요구사항 문서를 승인한 순간 자기 컴퓨터에서 AI가 코드를 생성하게 둘 수는 없으므로 "approve"와 "continue"를 별개 행동으로 쪼갰다. 승인 후 다음 단계 담당자에게 문서를 보내고, 그 동료가 승인을 확인한 뒤 "continue"라고 해야 워크플로가 이어진다. **감사 추적 서명** — AI가 쓴 코드의 책임 소재 문제를 푸는 확장으로, 기본 audit.md가 누가 요구사항을 냈고 누가 승인했는지는 기록하지 않기에 `User`와 `Email` 키를 추가하고 `git config user.name`/`user.email`로 채워 각 이력의 주인을 특정한다. **question 도구 사용** — 원본은 Kiro용이라 질문을 `{phase-name}-questions.md`에 쓰고 사용자가 그 파일에 들어가 답을 적길 기대하는데, 주로 OpenCode를 쓰는 필자는 질문 생성 직후 OpenCode의 question 도구로 직접 묻고 답을 문서에 되써 넣는 확장을 만들어 IDE를 오가지 않게 했다.

기본 확장 중에서도 테스트·보안·복원력 하위 폴더에 담긴 대기업의 모범 사례를 높이 평가한다. 대표 예가 **속성 기반 테스트(Property Based Testing, PBT)** 요구다. 과거 AI가 단위 테스트를 쓸 때 커버리지 숫자를 좋게 보이려고 소스 코드를 바꾸거나 테스트를 나중에 손보는 일이 있었다 — 필자 표현으로 AI가 시험 문제를 내고 제 답을 고쳐 지표를 속인 셈이다. PBT는 고정된 단일 입력을 검사하는 대신 방대한 입력 조건을 무작위 생성하므로 코드가 미리 답을 외우기 어렵고, AI가 다음 입력을 알 수 없어 테스트를 조작할 수 없다.

결론적으로 필자는 학습 곡선이 사실상 없어 바로 집어 쓸 수 있다는 점, 대기업의 모범 사례에서 왔기에 동적 워크플로와 동적 팀 협업에 초점이 맞춰져 팀 프로세스에 맞춘 커스터마이즈가 편하다는 점, 각 개발 단계에서 팀원의 책임 범위가 명확해져 프로덕션 사고 시 근본 원인과 책임자를 추적하기 쉬워진다는 점을 이점으로 꼽는다. 다만 이 워크플로가 소프트웨어 생애주기 관리 스타일을 강하게 요구해 대화 중 명확화가 필요한 질문들이 훨씬 기술적이며, 워크플로를 온전히 익히려면 소프트웨어 공학 지식을 더 배워야 할 수 있다고 덧붙인다 — 물론 그건 개발자라면 어차피 배워야 할 기초라고 본다.

**적용 각도(참고용 메모)**: 승인과 실행을 분리하는 아이디어는 쿠키의 gate/approval 흐름(무인 배치에서 사람 승인 지점을 남기는 설계)과 같은 문제의식이다. 특히 AIDLC를 Agent Skills 로 전환한 절차(core-workflow.md → SKILL.md, rule-details → references/)는 기존 마크다운 규칙 묶음을 스킬화하는 일반 레시피로 재사용할 수 있다.
