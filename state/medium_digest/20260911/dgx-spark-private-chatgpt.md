## 한글 요약

NVIDIA로부터 DGX Spark를 받은 저자가 이를 개인용 셀프호스팅 ChatGPT로 만든 구축기다. Spark는 GB10 Grace Blackwell 슈퍼칩 기반의 소형 박스로 CPU·GPU가 128GB 통합 메모리를 공유해, 17GB짜리 모델을 올려도 컨텍스트 여유가 크다. 모니터·키보드 없이 책상 밑에 두고 SSH로 접속하며 Ollama를 올렸다. 모델은 4월에 Apache 2.0으로 공개된 dense 모델 Qwen3.6 27B(Q4_K_M 양자화 약 17GB)를 골랐는데, 이미지 입력을 받고 사고(thinking) 단계를 실제로 건너뛰는 토글이 있다는 점이 앱 설계에 영향을 줬다.

저자는 스트리밍 채팅창 수준의 Ollama 프런트엔드는 이미 흔한 "해결된 문제"라고 보고, 매일 쓰면서야 드러나는 문제 해결에 집중했다. 목표는 ① 대화를 넘나드는 장기 메모리, ② 최신 정보는 웹을 먼저 읽고 번호 인용을 다는 답변(로컬 모델은 학습 시점 이후를 모르면서 가격·날짜를 자신 있게 지어내므로), ③ 계정·격리가 있는 다중 사용자와 같은 대화를 실시간으로 함께 보는 공유, ④ 불안정한 연결(기차 안 휴대폰 터널 등)에서도 버티는 복원력이다. 전체는 약 3,100줄로 프레임워크·빌드 단계·npm·외부 API 키가 전혀 없다.

구조는 단순하다. FastAPI 단일 프로세스가 Ollama와 HTTP로 통신하고 브라우저에는 SSE로 중계하며, 저장소는 WAL 모드 SQLite, 옆에 웹 검색이 붙는다. 큐·캐시 서버·워커 풀이 없는 것은 "한 사람이 처음부터 끝까지 읽고 이해할 수 있는 책상 밑 소프트웨어"라는 의도적 선택이다. 마크다운 렌더러·HTML 새니타이저·코드 하이라이터는 로컬에 벤더링해 네트워크가 끊겨도 UI가 동작한다.

메시지 흐름의 핵심은 '영수증'이다. 질문은 전송 전 브라우저 localStorage에 먼저 저장되고, 서버는 SQLite에 기록한 즉시 채팅 id를 담은 첫 프레임을 돌려준다. 브라우저는 이 프레임을 받아야 로컬 초안을 지운다. 이후 서버는 시스템 프롬프트 + 장기 메모리(인용하지 말고 활용하라는 헤더와 함께) + 최근 40개 메시지로 컨텍스트를 만들고, 필요하면 웹을 먼저 조회한 뒤 Ollama 스트림을 중계한다. 추론 토큰과 답변 토큰은 별도 채널로 보내 사고 블록과 답변이 동시에 렌더되고, 관전자가 있으면 인메모리 허브로 델타를 팬아웃한다. 턴이 어떻게 끝나든 finally 블록이 부분 답변을 DB에 쓰고 턴 락을 푼다.

저자는 "메시지가 모델까지 가는 길에 사라질 수 있는가"를 자문해 유실 지점 세 곳을 찾고 각각 다르게 복구한다. 서버에 도달하지 못한 경우엔 재전송 버튼(초안이 localStorage에 있으니 새로고침 후에도 유지), 저장은 됐는데 모델이 실패한 경우엔 중복을 피해 '다시 시도'(나중에 대화를 열어도 답 없는 질문을 감지해 완료 제안), 스트리밍 중 연결이 끊긴 경우엔 서버가 아직 생성 중일 가능성이 높으니 새로고침을 안내한다. 세 경우를 가르는 신호가 바로 첫 영수증 프레임의 수신 여부다. 또 10초간 토큰이 없으면 SSE 코멘트 프레임을 보내 스트림이 유휴 상태가 되지 않게 해, 큰 모델 로딩 중 ngrok이나 모바일 통신사가 연결을 끊는 것을 막는다. 턴 스트림은 JSON 본문을 가진 POST라 EventSource를 못 쓰고 fetch 리더로 직접 읽으며, 공유 관전 피드는 GET이라 EventSource의 자동 재연결을 활용한다.

웹 그라운딩은 4단계로 질문당 3~8초가 추가된다. ① "그거 가격은?" 같은 문장을 대화 맥락으로 독립 검색어로 재작성(temperature 0, 40토큰 제한, 사고 끔, 실패 시 원문 사용). ② ddgs 메타검색 라이브러리로 DuckDuckGo를 조회하고 다른 엔진으로 폴백. ③ 상위 7개 결과를 병렬로 가져오되 페이지당 12초·2MB, 전체 25초 예산을 둬 느린 서버 하나가 답을 붙잡지 못하게 하고, 스크립트·내비게이션·푸터·폼·한 단어 줄을 걸러 본문만 남긴다. ④ 페이지당 3,200자, 총 24,000자로 자르되 페이지 상한을 먼저 적용해 한 페이지가 나머지를 밀어내지 못하게 한다.

배치 위치에서 얻은 교훈도 공유한다. 검색 결과를 시스템 프롬프트가 아니라 질문 바로 앞에 붙였는데, 대화가 길어지면 시스템 프롬프트는 멀리 떨어지고 모델은 질문 근처 내용에 훨씬 큰 가중치를 두기 때문이다. 이 턴에만 컨텍스트 창을 16,384로 늘려 페이지가 조용히 잘리지 않게 했다. 지시문은 [1][2] 형태의 인라인 인용, 자기 기억보다 소스 우선, 소스 간 불일치는 골라내지 말고 드러내기, 그리고 오늘 날짜 명시(모델은 날짜를 모르므로)를 요구한다. 소스는 메시지와 함께 저장되고, 검색이 실패해도 "웹을 참조하지 않았다"는 경고와 함께 답은 나간다.

'메모리'라는 단어의 두 의미를 구분한 점도 짚는다. 대화 기록은 대화별(최근 40개 재생), 장기 메모리는 사람별·전역(모든 대화의 시스템 프롬프트에 주입되는 짧은 사실들)이다. 사이드바에서 관리하거나 대화 중 "기억해줘" 식 문구를 정규식으로 잡아 저장하며(대소문자 무시 중복 제거), 공유 대화에서도 타인에게 노출되지 않는다.

다중 사용자는 의도적으로 평범하게 만들었다 — PBKDF2-HMAC-SHA256(20만 회) 해시, HMAC 서명 세션 쿠키, 존재하지 않는 사용자명도 더미 해시를 비교해 응답 시간으로 구분되지 않게 하는 로그인 스로틀, 조회 후 if문이 아니라 SQL 자체에 박은 소유권 조건, 그리고 접근 불가 대화에 403 대신 404를 돌려 id 추측으로 존재 여부를 알 수 없게 했다. 공유는 멤버 테이블과 관전자별 asyncio 큐 기반 인메모리 pub/sub로 구현했고, Ollama가 기본적으로 한 번에 하나만 생성하므로 대화마다 15분 만료 턴 락을 둬 두 사람이 섞어 쓰거나 버려진 탭이 대화를 영구히 잠그는 일을 막는다. 특히 강조하는 보안 요소는 SSRF 가드다 — 검색 결과를 열기 전 호스트를 해석해 사설·루프백·링크로컬·예약·멀티캐스트 대역이면 거부해, 오염된 검색 결과가 페이지 리더를 내부망 탐지 도구로 악용하지 못하게 했다. 모델 출력은 DOM에 들어가기 전 모두 새니타이즈한다.

한계도 솔직히 적는다. 단일 프로세스·단일 SQLite 파일이고 자체 HTTPS가 없어 localhost나 TLS 프록시 뒤에 둬야 하며, 인메모리 허브라 공유 상태와 턴 락은 프로세스와 생사를 같이한다. 본문 추출은 휴리스틱이고 자동 검색 여부 판단은 정규식 기반이라 가끔 불필요하게 검색하거나 놓친다. 진짜 병목은 병렬 슬롯마다 KV 캐시 비용을 치러야 하는 Ollama의 단일 생성이다. 코드는 아직 비공개이며 추후 GitHub 공개 예정이라고 한다.

**적용 각도(참고용 메모)**: 알터(Hermes)류 에이전트의 웹 그라운딩·메모리 설계에 바로 참고할 패턴 — 근거 블록을 시스템 프롬프트가 아닌 질문 직전에 배치, 페이지별 상한 선적용, 영수증 프레임 기반 유실 판별, SSE 하트비트, 페치 전 SSRF 대역 차단.
