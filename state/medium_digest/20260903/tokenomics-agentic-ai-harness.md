## 한글 요약

엔터프라이즈 에이전틱 AI의 초점이 "에이전트 개발"에서 "스케일에서의 일관된 운영"으로 넘어갔고, 그 중심 개념이 **하니스(harness)** — LLM 자체가 아니라 LLM 주위에 신뢰성·책임성을 보장하는 실행 관리 구조를 짓는 것 — 라는 전제에서 출발한다(Anthropic이 에이전틱 코딩 맥락에서 촉발한 개념이지만 모든 에이전트 설계에 적용된다는 입장). 하니스의 빌딩 블록: 추론 루프(계획 생성→실행→반성→적응), 컨텍스트/메모리 관리(STM 요약 저장, STM→LTM 승격), Evals(LLM-as-a-Judge), 보안, 가드레일(프롬프트 인젝션·도구 오용·메모리 오염 방어), 그리고 감독자가 아닌 일급 시민으로서의 human-in-the-loop.

글의 **핵심 주장**은 비용 구조에 대한 것이다: 우리는 보통 LLM 호출을 (a) 추론/계획 수립과 (b) 에이전트 기능 실행(요약, 이메일 생성 등)으로만 생각하지만, 실제로는 **메모리·평가·가드레일 같은 비기능(non-functional) 호출이 기능 호출의 2~3배**에 달할 수 있다. LLM-as-a-Judge는 응답마다 두 번째 LLM을 돌리는 것이고, 가드레일도 마찬가지다 — OWASP·IBM 백서에서 정리된 16가지 에이전틱 리스크(기만적 행동, 목표 조작, 도구 오용, 메모리 오염, 연쇄 할루시네이션, 권한 침해, 자원 과부하, 다중 에이전트 공모, 인간 조작, 페르소나 편향 등)의 완화책을 중앙 가드레일 계층 하나에 몰아넣는 건 비현실적이며, 유스케이스별로 각 플랫폼 컴포넌트에 구현해야 하는데 **각 가드레일 구현이 하나 이상의 LLM/SLM 호출로 치환**되어 토큰 소비를 복리로 불린다.

이 비용을 관리하려면 **관측성(observability)이 선결 조건**이다. 저자는 OpenTelemetry 기반 계측을 제안한다: W3C trace context를 우선 채택하고, 'AI 태스크' 하나를 하나의 trace로 앵커링해 모델·도구 호출을 자식 span으로, 재시도는 같은 trace에 링크된 새 span으로 다루며, fan-out/fan-in은 fork가 아니라 링크로 표현하고, ID에는 의미를 넣지 않는다(의미는 attribute에). trace_id를 시스템 횡단 AI 상관 ID로 쓰자는 제안. 빌드타임 관측성(배포 전 구조·설계 검증)과 런타임 관측성을 구분하면서, 목표 드리프트나 재귀 루프 같은 가장 위험한 정렬 리스크는 동적으로만 드러나므로 런타임 쪽이 더 중요하다고 강조한다.

**인프라·추론 사이징** 절에서는 LangGraph+AKS 참조 시나리오로 구체적 볼류메트릭스를 제시한다(동시 에이전트 5개 기준: 10 vCPU/30GB RAM, 파드당 캐시 5GB, 일 1GB 텔레메트리, 벡터 데이터 ~25GB). LLM 추론은 Prefill(첫 토큰까지)과 Decoding(나머지, 전체 지연의 80%+)으로 나뉘며, 배치 시나리오는 처리량 최적화(GPU 적재→병렬화→배치 크기 최대화), 스트리밍은 첫 토큰 지연이 관건이다. RAG는 컨텍스트 윈도우를 꽉 채우는 특성상 첫 토큰 지연조차 크게 늘어난다. 이를 에이전트로 확장하면: 토큰 지연 ↔ 에이전트 처리 지연, 첫 토큰 ↔ 첫 에이전트 완료로 매핑되고, 멀티 에이전트 오케스트레이션에선 선행 에이전트 출력+실행 상태가 후행 에이전트 입력 컨텍스트에 계속 실려가므로 컨텍스트 윈도우 요구량이 누적된다.

흥미로운 전망 하나: 광고 브로커링처럼 **에이전트 브로커링 플랫폼** — 태스크에 에이전트 제공자들이 입찰하고 가장 신뢰성 있고 비용 효율적인 쪽이 낙찰받는 — 이 가까운 미래에 등장하리라 본다. 결론은 명료하다: 비기능 LLM 호출을 비용 관점의 일급 시민으로 취급하고, OTel 시맨틱 컨벤션 수준의 로깅을 깔아야 에이전틱 AI가 프로덕션에 간다.

**적용 각도(참고용 메모)**: 우리 llm_client.py의 "구독(claude -p) 우선 + LiteLLM 폴백"이 바로 이 글이 말하는 tokenomics 의사결정 — 다음 단계로 콜별 목적 태그(기능 vs 비기능: extract_keywords 같은 보조 호출)를 로그에 남기면 어떤 호출이 비용을 먹는지 이 글의 프레임대로 측정 가능.
