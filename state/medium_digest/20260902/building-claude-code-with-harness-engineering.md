## 한글 요약

Claude Code 를 "프레임워크"가 아니라 **하네스(harness)** 로 보고, 그 23개 구성요소를 파이썬으로 하나씩 재구성하며 설명하는 장문 튜토리얼이다(코드는 저자의 GitHub `claude-code-from-scratch` 레포). 저자의 출발점은 Claude Code 가 출시 6개월 만에 연환산 매출 10억 달러를 넘긴 이유가 더 좋은 프롬프트가 아니라 모델 주위의 하네스 — 스트리밍 에이전트 루프, 권한 게이트가 붙은 툴 디스패치, 긴 세션에서도 모델을 집중시키는 컨텍스트 관리 계층 — 였고, 그 하네스는 재현 가능하다는 것이다.

**하네스 엔지니어링 4원칙.** (1) 결정의 유일한 원천은 모델이다 — 하네스는 모델 출력으로 분기하지 않고 모델이 요청한 것을 실행만 한다. (2) 툴이 모델과 세계 사이의 유일한 인터페이스다 — 파일 읽기부터 서브에이전트 생성까지 전부 타입·스키마 검증된 툴 호출을 거친다. (3) 컨텍스트는 관리 대상 자원이다 — 매 턴 모델이 보는 것은 큐레이션·압축·의도적 주입의 결과이지 맹목적 누적이 아니다. (4) 권한은 절차가 아니라 선언이다 — 허용/차단/승인 필요를 조건문이 아니라 설정으로 정의한다. Claude Code 는 이를 따라 마스터 루프가 상태 없이 범용이고, 툴 레지스트리가 유일한 확장점이며, 컨텍스트 창 약 92% 사용 시 오래된 턴을 요약해 디스크에 남기고, 모든 툴 호출이 실행 전 규칙 평가를 통과한다.

**Phase 1 — 코어 에이전트 루프.** 가장 기본은 인식-행동-관찰 사이클의 `while True` 루프다: 모델 호출 → 응답을 히스토리에 추가 → stop_reason 이 tool_use 가 아니면 종료 → 툴 실행 결과를 user 메시지로 되돌림. 한 줄 버그 수정이든 대규모 리팩토링이든 코드는 같고 모델의 결정만 다르다. 툴 디스패치는 이름→핸들러 딕셔너리 한 줄(`handler(tool_input)`)이라 툴이 5개든 30개든 루프는 불변이며, MCP 확장도 레지스트리에 항목을 더하는 것과 같다. 저자가 강조하는 두 가지 세부: 툴 description 은 문서가 아니라 **지시**라서 모호하면 모델이 매번 bash 로 검색해버리고, 핸들러는 예외를 던지지 않고 에러를 문자열로 반환하는 계약을 지킨다. read 가 줄번호를 붙여 반환하는 것도 이후 write 가 줄 범위를 정확히 지칭하게 하려는 의도다.

TodoWrite 는 복잡한 작업에서 모델이 "흥미로운 중간 결과를 따라가다 옆길로 새는" 드리프트를 막는 **약속 장치**다. 실행 전 계획을 커밋하고, 매 툴 호출 후 현재 todo 상태를 시스템 리마인더로 재주입해 잊을 수 없게 만든다. 시스템 프롬프트의 "ALWAYS" 같은 강한 명령어가 실제로 계획 일관성을 좌우한다고 짚는다. 서브에이전트 컨텍스트 격리는 자식에게 완전히 독립된 messages 리스트를 주고 최종 텍스트만 부모에게 돌려주는 패턴이다 — 예시에서 부모는 툴 호출 1회, 자식은 25회 파일 읽기를 했지만 부모 컨텍스트는 요약 한 단락만 늘었다. 이것이 부모의 추론을 "파일 내용"이 아니라 "아키텍처" 수준에 머물게 한다.

**Phase 2 — 지식·컨텍스트 관리.** 스킬은 점진적 공개다: 시스템 프롬프트엔 각 스킬의 한 줄 설명만 넣고, 필요할 때 `load_skill` 툴 결과로 SKILL.md 전문을 주입한다. 스킬 100개를 깔아도 프롬프트는 100줄만 는다. 스킬은 모델을 똑똑하게 만드는 게 아니라 출력을 **일관되고 구조화**되게 만든다(코드 리뷰 예시에서 BUG/SECURITY/PERF/STYLE 분류와 배포 가능 여부 요약이 강제됨). 3계층 압축은 컨텍스트 크기를 측정해 임계치를 넘으면 최근 N개 메시지는 원문 유지, 그 이전은 별도 API 호출로 요약해 한 블록으로 치환, 요약을 `.agent_memory.md` 에 써서 다음 세션이 로드하게 한다. 파일 기반 태스크 의존성 그래프는 세션 스코프인 TodoWrite 를 확장한 것으로, ID·상태·우선순위·상위 의존 목록을 가진 태스크를 `.agent_tasks.json` 에 두고, 잠금(threading lock)으로 동시 접근을 원자화한다. 크래시 후 재시작해도 완료 태스크를 반복하지 않으며, 이후 멀티에이전트가 공유하는 기반이 된다.

**Phase 3 — 비동기 실행·멀티에이전트 팀.** 백그라운드 실행은 느린 작업(테스트, 컴파일, 마이그레이션)을 데몬 스레드로 돌리고 완료 결과를 큐에 넣어 매 턴 사이에 user 메시지로 주입하는 방식으로 메인 루프가 I/O 에 막히지 않게 한다. 이어서 JSONL 메일박스를 가진 상주 팀원 에이전트, IDLE→REQUEST→WAIT→RESPOND 상태기계로 통제되는 팀 통신 프로토콜, 중앙 조정자 없이 공유 보드에서 스스로 태스크를 집는 자율 에이전트, 파일 충돌 없이 병렬 작업하기 위한 태스크별 git worktree 격리를 다룬다.

**Phase 4~6 — 프로덕션·고성능·엔터프라이즈.** 실시간 토큰 스트리밍, 확장 툴셋과 파일 스냅샷(write 전 자동 백업 → revert), YAML 규칙 기반 권한 거버넌스(항상 거부/항상 허용/사용자 승인 3단계), 모든 툴 호출을 관찰·가로챌 수 있는 이벤트 버스와 라이프사이클 훅, 세션 저장·재개·포크가 Phase 4 다. Phase 5 는 asyncio.gather 병렬 툴 실행, 실행 중 인터럽트 주입, 프롬프트 캐싱과 KV 캐시 최적화, 공식 MCP SDK 로 외부 툴 자동 등록이다. Phase 6 은 JSONL 메일박스를 Redis pub/sub 으로 대체하고 worktree 라이프사이클의 엣지 케이스를 처리한 뒤 전체 메커니즘을 결합한다.

전체를 관통하는 메시지는 하나다: 하네스는 모델을 더 똑똑하게 만드는 것이 아니라, **신중한 실행이 가장 저항이 적은 경로가 되도록** 구조를 제공하는 것이다.

**적용 각도(참고용 메모)**: hermes/알터 에이전트 런타임 설계 점검표로 쓸 만함 — 특히 (a) 툴 description 을 "지시"로 다듬기, (b) 서브에이전트 결과만 부모에 반환하는 격리, (c) 92% 임계치 요약+디스크 영속 메모리, (d) 파일 기반 태스크 그래프의 잠금/의존성 — hermes-work-queue(Kanban) 워커 설계와 직접 비교 가능. 권한 3단계 YAML 선언은 `permissions.md` 게이트 구조와 대응.
