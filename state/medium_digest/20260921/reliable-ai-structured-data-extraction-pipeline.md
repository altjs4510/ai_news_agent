## 한글 요약

필자는 발주서·검사 기록·의료/인사 문서·사내 정책 문서처럼 기업 문서에서 구조화 데이터를 뽑아내는 자문 사례를 자주 다룬다. 구조화가 중요한 이유는 뽑아낸 값을 DB·업무 시스템·자동화 흐름에 곧바로 연결할 수 있어서다. 문제는 실제 기업 문서가 LLM이 처리하기 좋은 모양이 아니라는 데 있다. 다단 레이아웃, 여백 메모, 머리글·바닥글, 읽기 순서를 벗어난 텍스트, 여러 페이지에 걸치고 셀이 병합된 표, 스캔·손글씨, 차트 속 정보까지 섞여 있다.

필자가 강조하는 첫 번째 함정은 **오류가 LLM에 닿기 전에 이미 생긴다**는 점이다. 문서를 기계가 읽을 수 있는 형태로 바꾸는 파싱 단계에서 표가 평평해지거나, 값이 라벨과 떨어지거나, 행이 페이지 경계에서 끊기면, 이후 추출은 형식상 멀쩡하지만 내용은 틀린 결과를 낸다. 또 같은 문서 종류라도 조직마다 필요한 필드·검증 규칙·출력 구조가 달라서, 한 번 짠 스키마와 프롬프트를 여러 용도에 계속 재사용하기가 어렵다.

문서 추출의 흐름은 "값이 어디 있는지 알려주기"에서 "그 값이 무엇을 뜻하는지 설명하기"로 옮겨 왔다. 초기에는 OCR에 템플릿·좌표·키워드·정규식 규칙을 붙였는데, 레이아웃이 조금만 바뀌어도 규칙을 추가해야 했다. 이후 문서 이해용 ML 모델이 텍스트 블록·표·키-값 쌍을 인식하게 됐지만, 조직 고유 문서마다 라벨링 데이터를 만드는 비용이 컸다. LLM은 학습 없이 필드의 의미만 설명하면 처음 보는 문서에서도 원하는 구조로 값을 돌려준다는 점에서 유연성이 크다.

LLM 기반 구현 방식은 몇 갈래다. ① 먼저 텍스트/마크다운/HTML로 파싱한 뒤 LLM에 넘기는 parser-first 방식(레이아웃 보존이 관건), ② 페이지 이미지를 비전 LLM에 직접 넣는 방식(시각 맥락은 잘 살지만 느리고 비싸며 근거 추적이 어려움), ③ 텍스트·표는 일반 파서로, 차트·도면은 비전 모델로 해석해 원래 위치에 끼워 넣는 하이브리드 방식. 여기에 에이전틱 워크플로우를 얹으면 샘플 문서 분석, 스키마·프롬프트 생성, 결과 검사와 수정까지 단계별 에이전트가 나눠 맡는다. 다만 필자는 엔지니어링 부담이 사라진 게 아니라 **규칙·템플릿 관리에서 파서·스키마·프롬프트·검증 규칙·평가셋·배포 설정 관리로 옮겨갔을 뿐**이라고 짚는다.

신뢰할 수 있는 파이프라인의 구성은 다음 순서다. 레이아웃과 요소 간 관계를 보존하는 파싱 → 무엇을 어떤 구조로 뽑을지 정하는 스키마(직접 작성하거나 과업 설명·원문에서 LLM으로 추론, 한 번 승인하면 버전 관리하며 재사용) → 파싱 결과·스키마·프롬프트를 LLM에 넣어 추출 → 스키마 대비 필수 필드·타입 검증. 그런데 파싱 단계에서 틀린 숫자가 들어와도 "올바른 필드에 들어간 유효한 숫자"라면 스키마 검증을 통과해 버린다. 그래서 사람이 확인한 정답 데이터와 비교하는 **정확도 평가**가 필요하고, 운영 중 정답이 없을 때는 원문 인용·값 위치 표시·신뢰도 점수로 사람 검토를 돕는다. 마지막으로 앱이 문서를 보내면 결과를 돌려주는 API 형태나, 드라이브·SharePoint 같은 소스를 주기적으로 긁어 DB·ERP에 적재하는 ETL 형태로 배포한다.

실습 예로 오픈소스 Unstract를 썼다. 노코드 Prompt Studio에서 LLM·파서 조합을 고르고, 필드마다 추출 프롬프트와 출력 타입(텍스트·숫자·날짜·JSON)을 지정하는 방식이다. 레이아웃이 지저분한 발주서 샘플에 LLMWhisperer 파서를 붙였더니, 행 구조와 페이지 간 레이아웃이 충분히 보존돼 값을 제대로 뽑았다.

클라우드판의 베타 기능 Agentic Prompt Studio는 요약 에이전트가 후보 필드(이름·설명·타입·예시값)를 제안하고, 조정 에이전트가 문서마다 다르게 붙은 라벨을 같은 필드로 합치고, 마무리 에이전트가 이를 JSON Schema로 만든 뒤 추출 프롬프트까지 생성한다. 각 단계마다 사람이 검토·승인한다. 손으로 쓴 입사지원서에서는 모든 값이 정답과 일치했지만, 필자는 정답과 추출이 같은 문서에서 나온 **표본 내 일관성 확인**일 뿐 독립적인 정확도 측정은 아니라고 선을 긋는다. 건축 도면에서는 좌우 텍스트 칸의 필드는 잘 제안했지만 도면(다이어그램) 쪽 필드는 놓쳤다. 사람이 스키마에 치수 객체를 추가하고 다시 돌리자 전부 맞게 추출됐다. 스키마 검토에 사람이 개입해야 한다는 근거다.

배포 쪽에서는 Prompt Studio 프로젝트를 도구로 내보내 워크플로우에 넣었다. 같은 도구를 API와 ETL 양쪽에 재사용했다. API는 Postman 컬렉션으로 코드 없이 테스트했다. ETL은 Google Drive 폴더를 소스로, 무료 등급 PostgreSQL(Aiven)을 목적지로 연결해 매시간 새 발주서를 긁어 적재하도록 구성했다.

필자가 정리한 한계는 이렇다. (1) 추출 품질은 파이프라인 전체에 달려 있다. 파싱에서 잃은 정보는 모델이 되살리지 못하고, 파싱이 맞아도 스키마가 틀리면 결과가 틀린다. (2) 이 도구의 정확도 평가는 개발용 문서로 평가까지 하는 구조라 과대평가되기 쉽다. 스키마·프롬프트 개발용 문서와 **처음 보는 문서로 된 홀드아웃 테스트셋을 분리**해야 한다. (3) LlamaParse 쪽 논문처럼 단일 종합 점수로는 오류 원인을 알 수 없다. 순서와 무관한 값 F1과 단어·페이지 단위 근거(grounding) F1을 함께 보는 편이 낫다. (4) 발주서 품목의 추가 정보가 자재번호로 연결된 별도 BOM 문서에 있는 경우처럼 **문서 여러 개에 걸친 추출**에서는 올바른 스키마를 만들지 못했다. (5) 추출값의 원문 위치 하이라이트가 근처만 가리키는 경우가 있다. (6) 긴 문서는 후보 필드가 수백~수천 개로 불어나 사람이 대거 쳐내야 한다. 그래서 요구사항을 자연어로 받아 스키마를 역으로 추론하는 방식이 필요하다고 주장한다(필자 팀의 GAIK 툴킷 소개).

**적용 각도(참고용 메모)**: 크롤링 상세페이지·사내 문서에서 속성을 뽑는 라벨링/추출 작업에 "스키마 검증 통과 ≠ 정답"과 홀드아웃 평가셋 분리 원칙을 그대로 적용할 수 있음.
